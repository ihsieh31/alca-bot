# Architecture

Alca Agent is a local-first agent OS. The **core** runs on the user's computer, binds only to loopback, and owns all state in one SQLite file plus durable, inspectable memory in the same file. Every other surface (desktop UI, phone PWA, optional bridges) reaches the core through a **sidecar** that speaks the Alca Event Protocol over an end-to-end encrypted **Alca Link**.

Alca is always a **team of bots** (plan v3): a single-agent user is a team of one. The default bot is created on first launch; threads, jobs, approvals and browser Spaces carry `bot_id`. Hard rule: no source file over 800 lines (`scripts/check-file-size.ts`, CI).

## Trust boundaries

```
 phone PWA ─┐                                    ┌─ LinkHost in the core (outbound only; no inbound port)
 hands  ────┼─(E2E sealed frames, pinned keys)──►│  relay sees ciphertext, device ids, sizes, timing
 (LAN path ─┘  optional, same handshake)         └─► allow-listed RPC per device scope ──► core
 desktop UI ──(loopback + local token)──► core HTTP API (never reachable from Link)
 core ──► policy gateway ──► audit_log (written BEFORE execution) ──► tool / engine / browser / hands
```

- The core refuses to start when bound to a non-loopback address or when required secrets are missing (`core/src/safety.ts`).
- `initiator` (who caused a run: user / schedule / agent / webhook) is separate from `actor` (who emitted an event). Policy decides on the initiator.
- Payment, send, delete and publish always need a human yes. This is a host constant (`ALWAYS_CONFIRM_ACTIONS`), not a setting.
- Threat model for Link, the relay, the PWA host and hands: [SECURITY.md](SECURITY.md).

## Data flow of one turn

Phases are pure functions returning a verdict (`continue` / `jump` forward / `await` human / `halt`). Each step emits protocol events and persists to the store.

| #   | Phase        | What happens                                                                                                                           | Events                                                                             | Store                                    |
| --- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------- |
| 0   | (entry)      | User message, schedule or webhook arrives; a `turn` job and a run are created                                                          | `run.started`, `message.completed` (user)                                          | `runs`, `jobs`, `job_events`, `messages` |
| 1   | `prepare`    | Resolve engine, stable prompt layer (cache-safe) + volatile layer; checks-before-model for routines (nothing new → halt with 0 tokens) | —                                                                                  | —                                        |
| 2   | `recall`     | Budgeted memory recall (CJK FTS; embeddings only if a local model is plugged in)                                                       | —                                                                                  | `memories` read                          |
| 3   | `infer`      | Engine streams the answer                                                                                                              | `message.delta`* → `message.completed`                                             | `messages`                               |
| 4   | `plan_tools` | Requested tool calls grouped by path claims into parallel batches                                                                      | `tool.requested`                                                                   | `job_events`                             |
| 5   | `gate`       | Gateway evaluates each call (deny > ask > allow, always-confirm classes forced to ask) and writes the audit row first                  | `approval.requested` / `approval.resolved`, `question.asked` / `question.answered` | `audit_log`, `approvals`                 |
| 6   | `execute`    | Run allowed calls; outbound activity marks the job `outbound_observed` (never auto-retried); browser CAPTCHAs become a handoff         | `tool.completed`, `handoff.requested`, `error`                                     | `jobs`, `job_events`                     |
| 7   | `reflect`    | Loop guard; decide whether to loop back to `infer` as a new step or finish; background learning review is queued                       | —                                                                                  | —                                        |
| 8   | `persist`    | Close the run with a reason, flush run events                                                                                          | `run.finished{reason}`                                                             | `runs`, `run_events`                     |

Jumps only go forward inside one pass (`isForwardJump`); another engine step is a new pass (`repeat` verdict, only from `reflect`), bounded by the loop guard and `maxPasses`. `await` re-enters the same phase after a card is answered; `halt` always routes through `persist`, and so does a phase that throws, so a run is never left open.

## P1 implementation notes

### Runner and phases (`core/src/runner.ts`, `core/src/phases/*`)

Each phase is `(state, ctx) => Promise<verdict>`; the state is replaced, not mutated. `ctx.deps` carries the store, job runtime, gateway, engine, host tools, event emitter and the human latch. `AlcaCore.send` is phase 0: it creates the run, the `turn` job, persists the user message, emits `run.started` + `message.completed`, then hands off to the runner. Every event goes through one `emit`: validated by `RunEmitter`, appended to `run_events`, then published on the in-process bus (surfaces subscribe there).

Two kinds of engines share the pipeline:

- **Host-loop engines** (`ownsToolLoop: false`, e.g. `ScriptedEngine`, later direct API) return tool calls; `plan_tools` batches them by path claims, `gate` authorizes each through the gateway (approval / question cards → `await`), `execute` runs them via `gateway.execute` (re-checks the persisted approval), `reflect` loops back with the results.
- **Tool-owning engines** (`ownsToolLoop: true`, Claude Code) run their own tools. `infer` records their calls as observed `tool.requested` / `tool.completed`, and their permission prompts arrive through `onPermission`, which runs the same gateway and card flow (blocking inside `infer`). The CLI's own question tool becomes a question card; the answer goes back as a deny-with-message so the model receives it without the CLI's interactive UI.

### Prompt-cache discipline (`core/src/prompt.ts`)

`buildStablePrompt(profile, toolNames)` is pure and sorted, so the system prompt is byte-identical on every turn (tested). Volatile context (clock, initiator, attended) is a separate layer; recalled memory (at most one item) is fenced as `<alca:recalled>` data inside the **user** message. Engines whose system prompt is fixed at launch (`systemPromptAtLaunch`) put the volatile layer at the top of the user message; the CLI only ever sees the stable layer on its command line.

### Loop guard (`core/src/loop-guard.ts`)

Observes every completed call (host-run or engine-run) and counts three patterns: identical failing calls, A-B cycles, and no-progress (same call, same result). Counts go through `loopGuardVerdict` with the `engineering.loopGuard` thresholds: attended runs get one `error{code: loop_guard.warn}` per pattern; unattended runs are hard-stopped (`loop_guard.stop`, engine interrupted, run `failed`).

### Engines (`engines/src`)

`EngineCapabilities` is plain JSON: kind, persistent process, streaming, resume, interrupt, ownsToolLoop, native permission modes, how permission prompts arrive, system prompt at launch, prompt cache, images.

`ClaudeCodeEngine` keeps one `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` process per thread. A turn is one stdin line; stdout NDJSON is parsed (`ClaudeStreamParser`) until the `result` line. The process restarts only when `launchConfigHash` (engine, model, cwd, stable prompt, permission mode, env, extra args) changes or it died; the new process gets `--resume <session id>` (stored per thread in `engine_sessions`). Interrupt writes the stream-json `control_request {subtype: interrupt}`; if the turn has not ended after a grace period the process gets SIGINT. Permission prompts: the CLI is launched with `--mcp-config` pointing at our stdio MCP server (`claude/permission-mcp.ts`, Node built-ins only) and `--permission-prompt-tool mcp__alca__approve`; the server forwards each prompt to a loopback `PermissionBridge` (random port + bearer token), which calls the engine turn's `onPermission`. Everything fails closed: no active turn, bad token, unreachable bridge → deny. The CLI always runs in its `default` permission mode; our two levels are applied by the gateway, not by the CLI.

### Policy (`policy/src`)

`decide(rules, req, level)`: unknown class or any malformed rule → deny; deny rule → deny; always-confirm class (`payment`, `send`, `delete`, `publish`, from `@alca/config`) → ask even under an allow rule; explicit ask / allow rules; then the level (`autonomous` allows, `confirm_each_step` asks for everything but reads). `classifyToolCall` only escalates (e.g. `Bash rm …` → delete, `git push` → publish, `curl -X POST` → send); it is a floor, not a guarantee. `ActionGateway.authorize` writes the audit row before anything runs and persists the approval card; `resolveApproval` resolves once (DB trigger + `WHERE status='pending'`) and audits the resolution; `expireAllPending` runs on restart.

### Jobs (`jobs/src`)

`JobRuntime` changes state and appends a `job_events` row in the same (nestable, savepoint-based) transaction. Outbound event types (`outbound.sent|paid|posted`) set the sticky `outbound_observed` flag; the turn records one as soon as an outbound-class action is cleared to run (conservative). `recoverJobs` after a restart: any job whose events show outbound activity → `waiting` + `needs_review` (never auto-run; `review()` by a person); non-resumable kinds (turns) → cancelled; others requeued while attempts remain. `Scheduler.claimDue` advances the cursor with compare-and-set and creates the job in one transaction; `dispatch` runs only after that commit (at-most-once; missed slots are skipped).

### Desktop UI design (`apps/desktop/ui`, 素 Plain)

The desktop UI follows [design/DESIGN-SYSTEM.md](design/DESIGN-SYSTEM.md) (「素 Plain」): native macOS structure, one accent colour, plain words, technical detail one disclosure away. Structure: a source-list sidebar (需要你, 例行工作, conversations by date, then 資料庫: 團隊, 記憶與技能, 連接, 模型, 設定), a 52 px unified toolbar with icon buttons, the chat column (720 px) and an inspector for tasks and the browser. Library pages (記憶與技能, 團隊, 連接, 例行工作) share `library.css`: an 880 px column, a 22/600 page title, plain rows with inset hairlines and hover actions. 設定 (`ui/settings-view.ts`) is a settings window with a category list (一般, 通知, 模型, 裝置與連線, 瀏覽器, Telegram, 資料, 關於) and one pane; the sections themselves live in `settings-model.ts`, `settings-search.ts`, `settings-connection.ts`, `settings-system.ts`. Sheets (bot editor, 模型與供應商, 新增手機, 連線, Telegram) are 16 px-radius windows with a 15/600 title and a grouped form. Shared controls are in `forms.css` (popup buttons instead of segmented controls in forms, steppers, text fields) and `menu.ts` / `popup.ts`; icons are one 16 px outline set in `icons.ts`. Colour means state only: accent for selection and actions, orange for 需要你, red for destructive or failed, green for a completed check; no chips, gradients, letter tiles or pulsing dots. Review shots: `apps/desktop/scripts/shots-plain.ts` (1440×900, light and dark).

### Desktop server (`apps/desktop/src`)

Refuses to start unless the bind host is loopback and the token is strong (core startup check). `secrets.json` (0600) holds the generated local token; the UI URL carries it in the fragment (`#token=`), never in a query string. Every `/api/*` call needs `Authorization: Bearer`; Host must be our loopback host:port and a browser Origin must be same-origin (DNS-rebinding defense); responses carry a strict CSP. SSE (`/api/events`) replays the open runs first, so a reconnecting UI sees pending cards. The UI is plain TypeScript served with Node's type stripping (`node:module` `stripTypeScriptTypes`), no bundler.

## P2 implementation notes

### Bots (`store/src/repos/bots.ts`, migration 3)

`bots` table plus `bot_id` on `threads`, `jobs`, `approvals`; `browser_spaces` (owner `bot_id NOT NULL`, trigger: owner never changes; `worker_id` reserved for the router/worker split of plan v4). `BotRepo.ensureDefault()` runs in `openStore` (first launch creates one default bot and back-fills older rows). `AlcaCore.createThread(title, botId?)` assigns the default bot; a turn's `ctx.botId` is the thread's bot: it is the run's actor id, goes into the job, the audit detail, the approval row and `approval.requested.data.botId`, and reaches tools as `ctx.botId`.

### Tools and pre-gate inspection (`tools/src/registry.ts`, `core/src/phases/tools.ts`)

`RegisteredTool` = definition + optional `inspect(args)` + `run(args, {signal, actionClass, threadId, runId, botId})`; `hostToolsFrom()` adapts them to core host tools. `plan_tools` calls `inspect` before the gate: the result can only **escalate** to an always-confirm class (never lower), and its `summary` becomes the approval card text. A failing inspection keeps the declared class. `run` receives the class the gateway actually authorized, so a tool can refuse a step whose live class differs.

### Alca Browser (`packages/browser`)

```
desktop/phone ─► /api/browser (+ SSE channel) ─► BrowserHost ──(CDP over fd 3/4 pipe)──► our Chromium
agent tools  ─► BrowserAgent (ownership · takeover queue · gate) ─┘          profile: <data-dir>/browser/profile
```

- **Launch** (`launch.ts`): `--remote-debugging-pipe` (no port, nothing else can attach), `--user-data-dir` under our data dir, `assertOwnProfile` refuses the everyday Chrome / Chromium / Edge / Brave profile dirs (Chrome 136+ refuses remote debugging there anyway). Binary: `$ALCA_CHROMIUM`, a bundled Chrome for Testing in `<data-dir>/browser/bin`, then system paths. `CdpConnection` is a small flat-session client (ids, per-session events, timeouts, close rejects everything).
- **Spaces** (`host.ts`): `open({botId, title, threadId?, profile, persistent})`. `shared` = a new window in the shared profile (same logins as the person's own browsing); `isolated` = a fresh browser context (own cookie jar, discarded on close); `isolated + persistent` = a separate Chromium with its own profile dir `<data-dir>/browser/spaces/<id>` (cookies are per profile, so this is the only way to promise isolation that survives a restart). Tabs are tracked per Space with our own `tab_` ids; popups join their opener's Space; targets the host did not open are never touched. Records go to `browser_spaces`; on restart open records are closed.
- **Snapshots** (`snapshot.ts`, `page.ts`): `Accessibility.getFullAXTree` per frame. Same-process frames come from the page's frame tree; out-of-process iframes are auto-attached (`Target.setAutoAttach`, flat) and stitched in at their owner `<iframe>` (`DOM.getFrameOwner`). Shadow DOM is already flattened by the AX tree. Wrappers are folded, a control's own text is not repeated, selects list their options, output is budgeted. Actionable roles get `@N`; each ref maps to (session, frame, loader id, backend node, snapshot id). A ref is honoured only against the current snapshot **and** while its frame still has the same loader id; a navigation or a hand-back voids all refs (`StaleRefError` tells the model to re-snapshot). Page text reaches the model fenced as `<alca:page … trust="untrusted">`.
- **Actions**: navigate (http/https/about:blank only), click (real mouse events at the content quad in the main frame; `element.click()` inside child frames), type (`DOM.focus` + `Input.insertText`, optional clear / Enter), select, press, scroll, wait (ms or text), read, screenshot. Every function the page runs is host-authored; there is no agent-supplied JavaScript (the "evaluate" layer of the plan is simply not exposed).
- **Script mode** (`script.ts`): a JSON list of the same steps (`{"version":1,"steps":[…]}`), targets as `@N` or role + name locators. One tool call runs many steps; each still goes through ownership, takeover and the gate. A step whose live class needs an approval the script was not granted stops the script and reports `needsApproval`. `browser_recording` returns the bot's successful steps as a replayable script (locators, not refs).
- **Takeover**: `takeOver` / `handBack` change `controller`; while a person drives, agent steps queue (`status: queued`) and an interrupt rejects them. Person input (click / wheel / text / key in normalized coordinates) is accepted only while `controller = user`. A CAPTCHA seen in a snapshot hands the Space over automatically; `browser_handoff` lets the agent ask. Control changes are browser-channel events and, during a run of that thread, a run-scoped `handoff.requested`.
- **Sensitive-action gate** (`sensitive.ts`): before click / type / press / select / navigate the host reads the live element (role, label, form action and method, password / card fields, search role, default submit label) and the page URL, then classifies: payment / send / delete / publish name patterns (中文 + English), card-data fields, checkout pages, Enter-to-submit uses the form's submit label, sign-in and search forms are not "send", plus domain rules (PayPal, Stripe Checkout, Google Pay, LINE Pay, 街口, 綠界, 藍新, Gmail / Outlook send, X / Threads post). The always-confirm classes are the frozen `ALWAYS_CONFIRM_ACTIONS`; such a step runs only if the gateway authorized exactly that class for this call (`stepAllowed`). Tools' `inspect` uses the same classifier so the card appears before anything runs. This is the action layer; the network layer below sits under it.
- **Network-layer gate** (`network.ts`, P13): `TabDriver.onSession` hands every Space session (the tab, each OOPIF, each worker; children are auto-attached with `waitForDebuggerOnStart` and released only after `Fetch.enable`) to `NetworkGate.attach`, which enables `Fetch` at the request stage. `classifyRequest` (method, path / query patterns, body field names for urlencoded / multipart / JSON, GraphQL mutation names, domain rules without a label) returns read / write or an always-confirm class. `BrowserAgent.step` brackets each step with `beginStep(granted)` / `endStep()`; a paused request of the granted class continues (also for a 3 s grace after the step), another always-confirm class calls `BrowserHostOptions.confirmNetwork` — on the desktop `networkConfirmer` (`apps/desktop/src/browser-gate.ts`) authorizes through the core's `ActionGateway` (audit first), emits `approval.requested` into the owning thread or worker run, polls the stored approval and emits `approval.resolved` — and is held until the answer; no / no run / abort / timeout → `Fetch.failRequest(BlockedByClient)`. One open card per class per Space. `controller = user` passes everything. What happened is appended to the step's output and the `space.action` event's `gated`.
- **Channels** (`network.ts`, `host.ts`, next round R3): `NetworkGate.attach(space, session, kind, tab)` — on a `page` or `iframe` session it also turns on `Network` (for WebSocket events only, small buffers), `Network.setBypassServiceWorker`, the `__alcaRtc` binding and a `Page.addScriptToEvaluateOnNewDocument` script that makes `RTCPeerConnection` throw; any failure there throws, and the caller detaches (frame) or fails the tab. `Network.webSocketCreated` / `webSocketFrameSent` feed `classifyChannel` (the request rules: mutation names, password / card fields, domain rules); an always-confirm frame without a grant navigates the tab session to `about:blank`, notes `outcome: "stopped"` (kept for the next step if the step already ended), counts a strike per host (two → stop on open) and calls `BrowserHostOptions.notifyChannel` — on the desktop `channelNotifier` (`browser-gate.ts`): an audit row `browser.channel.stopped` plus an `error`-type notice (`browser.channel.stopped`) in the owning run. `BrowserHost.adopt` sends a browser-level `Target.setAutoAttach` filtered to `service_worker` / `shared_worker` (paused); `workerSpace` picks the Space by browser context, by owning process, or by a Space tab's origin in the shared profile, then `net.attach(space, session, type)` → `runIfWaitingForDebugger`, or `Target.closeTarget` when attach fails; other workers are resumed and detached. `chromiumArgs` adds `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`.
- **First-run Chromium** (`install/*.ts`, P13): `ChromiumInstaller.ensure()` (one run shared by concurrent callers): index JSON → `pickDownload` (platform map, https only) → `downloadFile` (resume via `.part` + `.part.json`, retries, `x-goog-hash` check) → `extractZip` into a staging dir → atomic rename to `<bin>/chrome-<platform>` → `installed.json`. States `checking → downloading → verifying → extracting → ready | failed` go out as the browser-channel event `browser.install` (no paths). `createBrowser({ autoInstall })` starts it at launch when nothing is found and makes the shared / isolated launchers wait for it.
- **Chrome cookie import** (`cookies/chrome-import.ts`, P13, macOS): `chromeProfiles` → `listChromeCookieDomains` (temp copy, host names only) → `readChromeCookies` (Keychain via `SafeStorageKeySource`, `deriveChromeKey`, `decryptChromeValue`, expiry filter) → `BrowserHost.importCookies(spaceId)` (persistent isolated Spaces only, `Storage.setCookies`). Desktop routes in `apps/desktop/src/browser-cookies.ts`.
- **Tools** (`tools.ts`): `browser_open, _navigate, _snapshot, _click, _type, _select, _press, _scroll, _wait, _read, _screenshot, _tabs, _run_script, _recording, _handoff`, registered in `@alca/tools`. Each call works on the calling bot's Space for the current thread (one task, one Space), opened on first use; another bot on the same thread gets its own Space.

### Desktop (`apps/desktop/src/browser.ts`, `ui/browser.ts`)

`--browser window|headless|off` (default window), lazy launch on the first Space; `--no-browser-download` turns off the first-run Chrome for Testing download. Routes: `GET /api/browser/status|spaces|spaces/:id` (status adds `chromium`, `install`, `cookieImport`), `POST /api/browser/install`, `GET /api/browser/chrome-import`, `POST /api/browser/spaces/:id/import-cookies`, `POST /api/browser/spaces`, `POST …/:id/takeover|handback|input|navigate|tabs`, `DELETE …/:id`, `GET /api/browser/events?watch=<spaceId>` (SSE: replayed `space.snapshot`s, channel events, and screencast frames for the watched Space only; frames are dropped while the socket is busy). The UI panel shows the Space switcher (with owning bot), profile badge, control chip, 接手／交還, tabs, address bar (editable only while you drive), the live frame (you click / type / scroll on it while you drive), the approval card for a pending browser step, and the last action. The offline demo serves a fake shop on its own loopback port.

## P2b implementation notes

### Host tools for tool-owning engines (`engines/src/claude/tools-mcp.ts`, `core/src/phases/engine-tools.ts`)

```
claude CLI ──stdio MCP──► tools-mcp.ts (stateless) ──POST /tool (loopback, bearer)──► PermissionBridge
                                                                                    └► engine turn's onToolCall
core infer.onToolCall ─► inspect ─► gateway.authorize (audit) ─► card / wait ─► gateway.execute ─► HostTool.run (browser)
```

- `EngineTurnRequest.onToolCall` is the host side; `ClaudeCodeEngine` exposes the turn's `tools` as a second MCP server `alcatools` (shared stdio loop `stdio-mcp.ts`, Node built-ins only) with the tool list in a 0600 temp file, and `--allowedTools mcp__alcatools` so the CLI does not prompt for them. The tool-list fingerprint is part of the process hash.
- The engine maps `mcp__alcatools__<name>` ↔ `<name>`: stream `tool.call` events and permission prompts carry the host's own names; a prompt for a host tool is flagged `hostTool` (core lets it through, because the call is gated when it arrives; a native CLI tool that happens to share a name is not).
- The CLI reports a tool_use on stdout and calls the MCP tool on another channel, in either order. `infer` matches them by tool name + canonical args (`canonicalArgs`), so one call has one `tool.requested`, its card refers to that `callId`, and the stream's `tool_result` closes it.
- `runEngineHostCall` repeats the host-loop steps: `inspect` may only escalate to an always-confirm class; deny → error result; ask → `approval.requested` (with `botId`), wait, `approval.resolved`; outbound noted before running; `gateway.execute` re-checks the approval; `run` gets the authorized class, `threadId`, `runId`, `botId` and (reserved) `workerId`. The browser tool's own `stepAllowed` then compares the live class with the authorized one. A denial or expiry never runs the tool.
- Browser behaviour is unchanged because the same `browserTools` run: bot-owned Space per thread, takeover queue, `space.*` channel events and frames, page text fenced `<alca:page … trust="untrusted">`. The stable prompt (fixed at CLI launch) names the host tools and the untrusted-page rule. Nothing secret crosses to the CLI: the bridge token is per engine and only opens the bridge; logins stay in the Chromium profile.

## P3 implementation notes

### Router and workers (`core/src/agents/*`)

```
person ─► thread turn = router turn (bot lock) ─► worker_start ─► WorkerSupervisor ─► worker run(s) ─► host tools (gated)
   ▲                                                                                     │
   └──── router turn ◄── router_inbox (persisted) ◄── report: inline result | summary + spl_ ◄┘
```

- `AgentSystem` (`system.ts`) wires one `RouterDesk`, one `WorkerSupervisor`, one `TriggerHub` and one `Watchdog` per host and publishes the agents channel. In router mode the thread turn is a router turn on the router's engine (which can be a different, cheaper model than the workers').
- **Router** (`router.ts`): one long-lived engine conversation per bot (`router_sessions`). Its only tools are `worker_start`, `worker_status`, `worker_stop` and `recall`; they change nothing outside Alca's own state, so the gateway sees them as `read`, and every effect is gated on the worker's own call. The core denies any engine-native tool a router turn asks for; the Claude Code router is also launched with the built-in tools removed (`--disallowedTools`, `claude.ts`). A bot lock (`lock.ts`) makes a bot's router turns take turns across threads.
- **Workers** (`workers.ts`): one per task, with its own id (`wkr_`), job, engine conversation (keyed by the worker id), runs and browser Space; full host tools and the worker prompt rules (do only the `<alca:task>`, never talk to the person, write the result last). `worker_start` returns at once; at most `maxConcurrent` per bot run, the rest are queued. A worker's cards are forwarded to the thread's stream; its text and tool calls stay on its own run.
- **Results** come back through `router_inbox`: a finished (or stuck-on-a-person) worker becomes an inbox row, delivered as a new router turn as soon as the thread is free. A pending row survives a restart. So the router is full duplex: it answers the person while workers run, and reports when they finish.
- **Inline vs spill** (`spill.ts`): a result up to `inlineChars` goes to the router whole; a longer one is stored in `spills` (append-only) and the router gets an extractive summary (`summaryChars`, no model call) plus the `spl_` id.
- **Recall chain** (`recall.ts`): every object has an id (`wkr_`, `spl_`, `trg_`, `tev_`, `str_`, `thr_`); `recall(id, offset?)` returns one object, paged, plus the ids next to it, so the model walks the graph a hop at a time. Only the calling bot's objects are visible.
- **Triggers** (`triggers.ts`): stage 1 code rules per source (mode, sender allow / block lists, keywords) at zero tokens; stage 2 a tool-less model judgment for candidates only (`wake` → router inbox, `skip` → logged). An event on a stream with live subscribed workers skips the router and goes to those workers (`worker_inbox`). Sources are pluggable; P3 ships `timer` (on the at-most-once scheduler) and `manual`. Every verdict is in `trigger_events`.
- **Watchdog** (`watchdog.ts`): a clock (`watchdogSec`) outside every worker stops workers that are stuck (no activity for `stuckSec` while not waiting for a person), looping (the same call `loopRepeats` times within the last `loopWindow` calls, whatever the results — the in-turn loop guard only catches repeated failures) or over budget (steps, running seconds without time waiting for a person, tokens). The stop is logged in `watchdog_events` and reported like any other result (`stopReason: watchdog.<kind>`).
- **Restart** (`WorkerSupervisor.recover`, after `AlcaCore.recover`): an unfinished worker resumes its engine conversation with a resume note; one whose job showed outbound activity becomes `needs_review` and is never re-run.

### Desktop (`apps/desktop/src/agents-routes.ts`, `demo-agents.ts`, `ui/workers.ts`)

`--agents router` (default) or `direct` (the P1 / P2 single-turn path). Routes: `GET /api/threads/:id/workers`, `GET /api/workers/:id`, `POST /api/workers/:id/stop`, `GET /api/workers/:id/events` (SSE: the worker's runs replayed, then live), `GET|POST /api/triggers`, `POST /api/triggers/:id/fire`. The offline demo has three scripted engines (router, worker, judge) covering parallel workers, a payment card in a worker's Space, a spilled result recalled page by page and a looping inbox poll the watchdog stops. The UI's worker panel shares the right column with the browser panel: a live list (in progress / finished), one worker's own stream with its cards and a stop button; the router chat shows reports as compact rows, and every worker approval card (chat and browser panel) has a bot › worker line that opens that worker.

## P4 implementation notes

Wire format: [PROTOCOL.md § Alca Link](PROTOCOL.md#alca-link-p4). Threat model: [SECURITY.md](SECURITY.md).

### Link (`packages/link`)

- **Identity** (`identity.ts`): one ECDSA P-256 key pair per device, created once. The core's lives in `secrets.json` (`link.identityKey`, JWK; replaced the P1 placeholder); the phone's is a non-extractable WebCrypto key in IndexedDB; a hands daemon's is in its state file (0600). Safety number = 4 groups of 4 hex digits of the SHA-256 fingerprint.
- **Pairing** (`spake2.ts`, `handshake.ts`): SPAKE2 over P-256 (RFC 9382, PAKE v2; v1 removed) on the 6-digit secret of a single-use code; inside the PAKE-keyed channel both sides exchange their identity keys signed over the transcript; the device also checks the core's fingerprint from the QR. A relay gets one online guess per code; nothing it records allows offline guessing. Point arithmetic is `@noble/curves` (`curve.ts`); details in [CRYPTO.md](CRYPTO.md).
- **Session**: signed ephemeral ECDH on every connection (forward secrecy; a recorded handshake cannot be replayed); `SecureChannel` seals each message with AES-256-GCM and a strict per-direction counter.
- **Host / client** (`host.ts`, `client.ts`): the core connects _out_ to the relay, proves it owns its mailbox, opens nameplates on request and turns each authenticated device into a `LinkPeer` (RPC both ways + pushed events). Devices try the core's LAN URLs first when allowed (Node: yes; an https page cannot open `ws://`), then the relay; reconnect with backoff; stop for good on `revoked`.
- **QR** (`qr.ts`): our own byte-mode encoder (level M, versions 1–10), SVG and terminal output; tests decode it with `zbarimg`.

### Desktop (`apps/desktop/src/link.ts`, `link-rpc.ts`, `link-routes.ts`, `hands.ts`, `pair.ts`)

- `--rendezvous <url>` turns Link on (`--link-lan <port>` adds the direct LAN listener, `--pwa-url` sets where the QR link points). Migration 5 makes `devices` the paired-device list: key fingerprint, `kind` (`phone` / `hands`), platform; a device key never changes and a device is revoked, never deleted.
- Routes (loopback only): `GET /api/link` (status, relay, safety number, devices), `POST /api/link/pairings` (code + QR SVG + link; scopes), `DELETE /api/link/pairings/:nameplate`, `POST /api/link/devices/:id/revoke` (permanent; live sessions end at once), `POST /api/link/devices/:id/scopes`. `pnpm desktop:pair` prints a code and a terminal QR.
- **Phone RPC** (`link-rpc.ts`): an explicit op table (default deny), each op with the scope it needs (`chat`, `approve`, `view_screen`, `control_computer`), checked against the store on every call. Watches (thread, worker, browser Space) push sealed events; video frames are dropped under back-pressure, events never are. The phone acts as `user:device:<id>`.
- **Hands** (`hands.ts`): online hands daemons register on connect; the `hands_*` host tools go through inspect → gateway → audit → card like any tool (a `hands_run` that deletes / sends / pays is still always-confirm), so a denied call never reaches the device.
- UI: the 新增手機 sheet (`ui/link.ts`) opens a code + QR beside the pairing steps, lists paired devices and revokes; safety numbers sit behind 安全碼 and in each device's tooltip. Paired devices are also listed in 設定 › 裝置與連線.

### Hands daemon (`apps/hands`)

Stateless: `pair <code> --rendezvous <url>` once, then `run --workdir <dir>`. The executor (`executor.ts`) resolves every path against the real path of its one work directory and refuses anything (symlinks included) that escapes; commands run with a clean environment (`PATH`, `LANG=C.UTF-8`, `HOME` = the work directory, plus an explicit pass list), in their own process group, killed as a group on timeout (1–600 s); output and file reads are capped (64 KiB default).

### Phone PWA (`apps/phone-pwa`)

An independent mobile design in 墨 Mono (shared `tokens.css`, its own layout and components): pairing (code or `#pair=` link, safety number), chat with streamed replies and compact tool / report rows, approval cards as bottom sheets (payment / send / delete / publish shown as always-confirm), a 等你決定 pill while cards wait, a workers sheet (one card per worker, swipe), the live Space frame with 接手 / 交還 and zoom, a thread drawer, devices and theme. No bundler: `scripts/build.ts` strips types with Node's built-in stripper, rewrites imports, copies Link's browser modules and writes a service worker whose precache list and version come from the built files. The relay can serve it (`--pwa`).

## P5 implementation notes

### Memory (`packages/memory`, `store/src/repos/memories.ts`, `skills.ts`, migration 6)

- **One memory per row, never overwritten.** `memories` rows carry the owning bot, `scope` (`shared` = the user model every bot of the team reads; `bot` = that bot's own notes), `kind` (fact / preference / person / project), the person's own words (`quote`, redacted), `origin` (`user` = said outright with 記住… or confirmed / edited by them; `inferred` = guessed from a turn, with a confidence) and provenance (thread, message, run, worker). An edit, a correction or a newer statement on the same subject inserts a new row that supersedes the old one (triggers refuse content updates and un-superseding). `MemoryService.learn` decides: stored, superseded, duplicate, confirmed, secret (dropped whole), forgotten (matches a tombstone), kept_confirmed (an inference never replaces something the person said).
- **Forgetting** deletes every version of the chain (hard `DELETE`, FTS rows go with it) and writes a tombstone: an HMAC digest of the normalized text plus 8-hex HMAC shingles of its content tokens, keyed per store (`memory_meta`). Extraction checks new candidates against tombstones so the same thing is not learned again; the person can clear the tombstones (「讓 Alca 可以重新學習」). See [SECURITY.md § Memory](SECURITY.md#memory-and-learning-p5).
- **Secret filter** (`redact.ts`): private keys, tokens, JWTs, bearer headers, URL credentials / secret params, labelled secrets, card numbers (Luhn), national ids and high-entropy strings. A candidate memory containing one is refused; a skill step has the value replaced by a marker.
- **Recall** is budgeted (`memory.recallTokens`, default 400) and goes into the router's **user** message as fenced `<alca:recalled>` data with a tag that says whether the person said it or Alca inferred it (stable system prompt unchanged). Search is CJK FTS; `Embedder` is an optional hook (reciprocal-rank fusion with cosine) and ships unset, so memory makes no network call.

### Learning in the core (`core/src/learning.ts`)

- `Learning` implements the core's turn hooks: `beforeTurn` handles 記住／忘記 before the pipeline (and tells the router what changed), recall feeds phase 2, `afterTurn` runs the rule extractor on what the person said about themselves. One switch (`advanced.learning`) turns curation, skill proposals and step notes off.
- The router gets two read-only tools, `memory_search` and `skill_load`, and passes **ids** to workers in `worker_start` (`memoryIds`, `skillId`); the core checks those grants (only memory the bot can read, only the bot's own active skill) and stores them on `workers.grants`. A worker sees the granted items and nothing else.
- **Skills**: after a worker succeeds with at least `memory.skillMinSteps` successful tool calls, its calls are drafted into a proposal (name, triggers, steps with their action class; text from the approval card or the tool's own description). It is saved only when the person approves (optionally with edits); versions are append-only and a decided version is final. A correction after a skilled run proposes a revision. A skill is advice, never a permission: every step still goes through the gateway, and payment / send / delete / publish are confirmed at run time (tested under 自主 with real Chromium).
- Events go out on the learning channel ([PROTOCOL.md](PROTOCOL.md#learning-channel-p5)).

### Desktop (`apps/desktop/src/memory-api.ts`, `memory-routes.ts`, `ui/library.ts`, `ui/skill-card.ts`)

`MemoryApi` is shared by the loopback routes (`/api/memory`, `/api/skills`) and the phone's Link ops. The 記憶與技能 library (sidebar) lists memory with search and kind / scope / source filters, each row with its provenance (which chat, 你說的 or 推測 + confidence, edited, uses); edit (a new version), confirm, rescope, forget (confirm dialog), export (JSON with history and skills), clear forgotten. The 技能 tab shows proposals and saved skills (enable / disable / edit / delete). A proposal also appears as a card at the end of the chat it came from (存成技能 / 編輯後存 / 不用), with 含一律確認 badges and a vermilion tag on pay / send / delete / publish steps.

### Phone (`apps/phone-pwa/app/memory.ts`, `skills.ts`, `learn-view.ts`)

A full-screen 記憶與技能 sheet from the thread drawer (or `#memory` / `#skills`): search, kind and source chips with counts, tap a row for its quote and facts, 沒錯 (confirm an inference), 編輯 (new version), 忘記 (confirm sheet that says the original chat messages stay), export via the share sheet or a download; a 技能 tab with proposals and saved skills (on / off switch). A proposal from the open thread shows as a quiet 學到一個做法 row at the end of the chat (it never interrupts) and opens a bottom sheet with the steps, the red 一律確認 markers and 存成技能 / 不用. Memory ops need the `chat` scope; skill decisions need `approve`.

## P7 implementation notes

### Team in the core (`core/src/agents/peers.ts`, `store/src/repos/team.ts`, migration 8)

- **Bot profiles.** A bot has a name, avatar (a character), a tone (one of six muted colours), a role (one line teammates route by), its own instructions, an engine + model, an approval level (`team` = the team's, `confirm_each_step`, `autonomous`), a browser profile (`shared`, `isolated`, `isolated_keep`) and a memory mode (`team`, `own`, `off`). One bot may be the **lead**: new conversations go to it and it decides whether to hand them on. The default bot can be edited but never archived; an archived bot cannot lead (triggers).
- **PeerDesk** gives every router three tools: `peer_ask` (a question, answered from the teammate's knowledge and memory), `peer_delegate` (work, done with the teammate's own workers and grants) and `peer_status`. Both return at once; the asked bot works in its own **peer conversation** (a thread with `peer_request_id`), and when nothing is left there the request settles and the answer goes back to the asking router as `<alca:peer-report>` in its inbox.
- **Rules.** The team rule (`auto`, `ask_delegate` default, `ask_all`) is a host policy rule, so the gateway asks with an ordinary card. Depth (default 2, at most 5), loops (a bot already in the chain is never asked again) and open requests (default 4) are refused and recorded, never silently dropped. Cards raised inside a peer conversation are shown in the person's conversation the chain started from (`rootThreadId`).
- **Narrowing.** A call in a peer conversation runs at the strictest approval level of every bot in the chain (`AlcaCore.levelFor`), and a connected-app call uses only the accounts every bot of the chain may use, at the lowest access any of them has (`ConnectorService.usable(botId, threadId)`). Always-confirm classes ask regardless.
- **Trail.** `peer_requests` keeps who asked whom with a fixed chain and one final status; `peer_events` is append-only (requested, approval, approved / denied / refused, started, card, answered, failed, stopped). `runs.bot_id` records which bot spoke, so a thread that hears from several bots (@mentions) keeps the byline of each message.
- **@mention.** `@name …` at the start of a message (longest name wins) or an explicit `botId` makes that bot answer in the same thread; it is not a delegation.

### Engines (`engines/src/http/*`, `apps/desktop/src/engines.ts`)

`OpenAICompatEngine` (chat completions with SSE, function calls assembled across chunks) and `GeminiEngine` (`streamGenerateContent` SSE, `functionCall` / `functionResponse`) are host-loop engines: every tool call goes through the same gateway as the others. History is kept per conversation key in the store; a key is read from the local vault at call time (`engine:<providerId>`) and only ever sent in the request header. `EngineSet` picks a bot's engine (the default engine, the default with another model, or a model service the person added) for its router and its workers. Presets: OpenRouter, Ollama, LM Studio (OpenAI-compatible) and Gemini; a remote service must use https, a local one may use http on loopback.

### Desktop + phone

`team-api.ts` is shared by the loopback routes (`team-routes.ts`) and the phone's Link ops (`link-team-ops.ts`). Desktop UI: `ui/team.ts` (團隊: roster with what each bot is doing, rules, 協作紀錄), `ui/bot-edit.ts` (the editor; 進階 holds everything beyond name, avatar, tone and role; 封存 asks in the editor's footer), `ui/mention.ts` (sidebar roster, 對 X 說 chip, @ completion), bylines and peer rows in `ui/timeline.ts`. Phone: `app/team.ts` (團隊 sheet, a bot's sheet, one request's sheet), `app/mention.ts` (@ list above the composer, the addressee chip), `app/team-view.ts` (shapes, words, pure helpers), bylines and peer rows in `app/chat.ts` / `app/timeline.ts`. ## P9 implementation notes

### Stable address and reconnect (`link/src/host.ts`, `client.ts`, `relay-protocol.ts`, `services/rendezvous/src/relay.ts`)

- **Mailbox.** `mailboxOf(pub)` = the first 128 bits of the SHA-256 fingerprint of the core's long-term Link key, so it survives core and relay restarts and relay moves; nothing is assigned by the relay.
- **Self-check.** `LinkHost.selfCheck()` runs every 15 min (and on 現在檢查): a `ping` on the relay socket (`pong` within 10 s) and a `probe` of its own mailbox over a fresh socket (`probeRelay`). On `offline`, `no_pong`, `not_listed` or `probe_failed` it drops the socket and registers again; `health` keeps the last check, the reason and the repair count for 連線 and the phone's 診斷 (`link.health`).
- **Endpoints.** `endpoints()` = the relay in use first, then the stable relay from `link.json` and any other known relay, plus the direct addresses; sent in `ready` and as a sealed `endpoints` event when they change. `setRelayUrl` tells live devices first, then re-registers on the new relay. `LinkClient` stores the lists with its credentials and tries direct → each relay, keeping the last one that worked; backoff with jitter, `stats` (retries, next try, connects, last online) drive the phone's reconnect banner (`app/reconnect.ts`).
- **Pairing tries.** On a wrong code the core sends `nameplate.reopen`; the relay counts claims per nameplate (5) and lets one claimer in at a time.
- **Desktop.** `link-prefs.ts` (`link.json`, 0600, URL checks), `link-routes.ts` (`GET/PUT /api/link/connection`, `POST …/check`), `ui/connection.ts` (the 連線 sheet, opened from 新增手機 → 連線設定…; relay, mailbox id and self-check sit under 技術細節).

### Codex CLI engine (`engines/src/codex/*`, `core/src/agents/codex.ts`)

`CodexEngine` spawns one `codex exec --json` per turn (`args.ts`: `--sandbox read-only`, `approval_policy="never"`, `-C <cwd>`, `-m` when a model is set, `resume <session id>` from the store; the stable prompt layer goes at the top of a conversation's first message, the prompt on stdin). `parse.ts` maps the JSONL stream (`thread.started` → session id, `item.*` for `agent_message` / `command_execution` / `file_change` / `mcp_tool_call` / `web_search`, `turn.completed` usage, `turn.failed` / `error`) onto engine events. Host tools reach Codex as an MCP server configured with `-c mcp_servers.alcatools.*`, the same stdio bridge as the Claude Code engine, its token in a 0600 file named by `ALCA_BRIDGE_FILE`. Interrupt = SIGINT, then kill; a crash or a missing CLI is reported, not retried blindly. `codexAgentEngines` builds a router + worker pair; `EngineSet` offers it as the 「Codex CLI」 choice (`CODEX_CHOICE_ID`) when the desktop has a Codex command (`--codex-bin`, `$ALCA_CODEX`, default `codex`). Tests use `engines/testing/fake-codex.ts`.

### Model-based memory extraction (`memory/src/model-extract.ts`, `core/src/extract-engine.ts`, migration 10)

`bots.memory_extract` is `rules` (default) or `model`. With `model`, `CombinedExtractor` runs the rule extractor (the floor) and `ModelExtractor`, which asks the bot's own engine through `engineCompletion` — a fresh conversation where every permission is denied and every tool call refused — for at most three JSON proposals. `parseModelCandidates` keeps one only when its `quote` is a whitespace-normalized substring of the person's text in this turn, its kind is known and neither body nor quote looks like a secret; confidence is capped at 0.9 and the item is `inferred`. Duplicates of the rules' result (by subject, body or quote) are skipped; a model error or timeout leaves the rules' result. The memory service then applies the secret filter, tombstones and confirmed-wins as for every candidate.

### Smoke tests (`apps/desktop/smoke/*`, `vitest.smoke.config.ts`)

`pnpm smoke` only; each `describe` is skipped unless its `ALCA_SMOKE_*` variable is set (RUNNING § 14). Never included by `vitest.config.ts`, so `pnpm test` and CI stay offline.

## P10 implementation notes

### Google account directory (`services/rendezvous/src/google.ts`, `accounts.ts`, `accounts-file.ts`, `relay.ts`)

- `GoogleTokenVerifier` (WebCrypto + fetch): RS256 against the JWKS, cached for `max-age` (60 s – 24 h), one refetch on an unknown `kid` per 30 s; `iss`, `aud` ∈ configured client IDs, `exp` / `iat` / `nbf` ± 120 s; returns `sub` (+ `email`).

## P13 implementation notes (agent features)

### Working folders (`core/src/workspace/workdir.ts`)

`BotWorkDirs` gives every bot one folder: `<data>/bots/<id>/work` by default, or the bot's `workDir` setting, checked every time it is used (absolute or `~/…`, symlinks of the nearest existing ancestor resolved, never `/`, the home folder itself, a system folder, Alca's data folder or a folder containing it). A setting that fails is not used: the bot runs in its default folder and the roster shows `workDirProblem`. Engines start there (`cwd`), and Alca's own file tools (`file-tools.ts`: `file_list` / `file_read` / `file_write` / `file_edit`, for every engine) resolve every path inside it with `confine` (`..` or a symlink out is refused). `--workdir` is the folder bots without their own work in.

### Guards (`core/src/workspace/guards.ts`, `AlcaCore.useGuards`)

`WorkspaceGuards` runs on every gated call: a file edit (Claude Code `Edit` / `Write` / …, Alca's file tools, an ACP edit kind with its `locations` → `paths`) outside the bot's folder asks first, even under 自主; with the bot's `shellReview` on, a shell command under 自主 goes to `ShellReviewer` (`shell-review.ts`); `beforeRun` snapshots every edit that is cleared to run; `noAsk` turns a card from a 提前做 worker into a denial.

### Undo (`core/src/workspace/journal.ts`, `store/src/repos/snapshots.ts`, migration 12)

`EditJournal.snapshot` stores each file as it was before the turn's first edit of it (`file_snapshots`: content, mode, `existed`; a file over `engineering.undo.maxFileBytes` or unreadable is recorded as `skipped`), keyed by the turn's top-level run (`turn_run_id`, so a worker's edits belong to the turn that dispatched it). `prune` keeps the newest `keepTurns` turns per conversation within `maxTotalBytes`. `undo(thread, turn)` refuses while the turn still runs, when it was undone or pruned, or when a later turn changed one of its files (`laterEdit`); otherwise it writes old contents back, removes files the turn created, and marks the rows undone. Routes `GET /api/undo/:thread`, `POST /api/undo/:thread/:turn` (`apps/desktop/src/workspace-routes.ts`, `workspace.ts`). UI: `ui/undo-strip.ts` — a strip above the composer with the newest undoable turn (files changed, when), 復原 behind a confirm dialog that lists the files, the server's reason when it refuses; disabled while the conversation's run is open and refreshed when it ends.

### Shell review (`core/src/workspace/shell-review.ts`)

Off by default, per bot (`shellReview`, `shellReviewEngine`, `shellReviewModel`). A shell command (Bash, `hands_run`, an ACP `execute` kind) the rules and level would allow is shown, fenced with `defuseAlcaTags`, to the bot's own router engine or the one picked for reviews (`EngineSet.forChoice`, confirm-each-step), in a fresh conversation with no tools. The first line must be LOW / MEDIUM / HIGH within `engineering.shellReview.timeoutSec`; HIGH, an error, a timeout or anything unreadable becomes a card. Every review is an audit row (`shell_review`).

### 提前做 (`core/src/agents/early.ts`, `store/src/repos/early.ts`)

`EarlyDesk` takes trigger events (and `POST /api/early` requests) for bots with `earlyWork` on, holds them through `quietHours` (`HH:MM-HH:MM`, the core's zone), caps them per day and in parallel (`engineering.earlyWork`), and runs each as a speculative worker at the bot's own level whose cards are denied (`EARLY_NO_ASK`). UI: `ui/early-view.ts` in 例行工作 lists the items (排隊中 with the quiet-hours end, 準備中, 草稿好了, 沒有完成) and marks drafts that came from 提前做; the bot editor's 進階 has the folder, review and 提前做 settings (`ui/bot-p13.ts`). ## P13 implementation notes (fixes, backups, conversation list, 設定)

### Turn timeout and the run cap (`core/src/runner.ts`)

`engineering.turnTimeoutSec` stops a thread or router turn that runs too long (time waiting for a person or for a slot is not counted): error `turn.timeout`, the engine is interrupted, and an engine that ignores the interrupt is closed after a grace so the run, its job, the slot and the router lock are released. `engineering.maxConcurrentRuns` (default 8) is one semaphore over every run with a conversation lane ahead of workers (workers leave one slot free so a bot can always answer); a run waiting on an approval gives its slot back.

### Router on every engine kind, one level vocabulary (`core/src/agents/*`, `config/src/levels.ts`)

An ACP or API bot's router is its own engine instance (no conversation shared with its workers) and an ACP router always runs in the agent's asking mode. The core stops a router turn whose engine ran a native tool that can change something without asking (`router.native_tool`; look-only ACP kinds and read-only native tools are exempt). `APPROVAL_LEVELS` / `TEAM_LEVEL` / `LEVEL_WORDS` / `effectiveLevel` / `strictestLevel` in `@alca/config` are the only level words the core, the team API, the engine set and both UIs use.

### Desktop server shape (`apps/desktop/src/app-context.ts`, `routes.ts`, `core-routes.ts`)

One `AppContext` (core, token, live settings, the feature services) and a declarative route table: method + path patterns with `:param`, 405 for a known path under another method, feature areas mounted by their first segment. Every bot engine other than the default comes from the P11 provider registry (the P7 model-service route is gone). `@alca/connectors` depends on tools / config / policy / store only; the host contracts (`HostTool`, `TriggerRule`, …) live in `@alca/tools`.

### Database backups (`store/src/backup.ts`, `apps/desktop/src/db-cli.ts`)

Before a pending migration runs on a database that already has data, `openStore` copies it with `VACUUM INTO` to `<data>/backups/state-v<from>-<time>.sqlite` (a new file, nothing to lose, is not backed up); the newest five are kept and a failed migration names the backup it made. `alca db backups | backup | restore <file|name>`: restore checks `PRAGMA integrity_check` and that the schema version is one this build knows, refuses while a core runs (`<data>/core.pid`, written and removed by `startDesktop`; a stale pid does not block), and moves the current file (and its `-wal` / `-shm`) aside as `state.sqlite.before-restore-<time>` instead of deleting it.

### Conversation list: paging, archive, delete tombstones (`store/src/repos/threads.ts`, migration 15)

`threads.list(limit, {before, archived})` pages by `(updated_at, id)` so equal timestamps never leave a gap. Archive sets `archived_at`. Delete (`erase`) removes the conversation's `messages`, `drafts` and `engine_sessions` and clears its title in one savepoint, but keeps the `threads` row with `deleted_at` set as a tombstone, because `runs`, `approvals` and `audit_log` point at it and are append-only by design. A tombstoned thread never lists, opens or archives again. `AlcaCore.deleteThread` refuses while a run is active, and while routines, enabled triggers or live workers use the thread (`ThreadInUseError` names them → HTTP 409). Link: `threads.list {limit, before, archived}`, `threads.archive` (scope `chat`), `threads.delete` (scope `approve`).

### Settings (`config/src/schema.ts`, `settings.ts`, `apps/desktop/src/settings-api.ts`, `settings-routes.ts`)

Keys nothing read are gone from the schema; `REMOVED_KEYS` lists them and `stripRemovedKeys` drops them from an old `config.json` before the strict parse, so the file still loads, each dropped key is warned once and is gone after the next save. `GET / PATCH /api/settings` (loopback only; paired devices cannot change settings) edits the person-facing part: simple — team level, learning, `devices.pushPreview` (`none` = no Web Push at all, logged as skipped; `notify_only` = the content-free ping); 進階 — new devices' default scopes (never `control_computer`), pairing on / off, a self-hosted https rendezvous, the log level. A change is validated by the same schema, written atomically to `config.json`, and applied at once where the running core reads it through `() => settings` (level, learning, push, log level); `devices.allowPairing`, `devices.defaultScopes` and `advanced.rendezvousUrl` are read once at start and come back in `pendingRestart` until the next start. The always-confirm classes are shown, never editable. `engineering` and the model list are left as they are. `advanced.browserAutoDownload` is read by the browser on every lookup (`BrowserSetup.autoInstall()`), so it applies at once, and only when the app started with its download on (`--no-browser-download` locks it off for that run). The other areas of the dialog (`ui/settings-model.ts`, `settings-connection.ts`, `settings-system.ts`) use the existing APIs — `/api/team` + `PATCH /api/bots/:id` + `/api/providers` for the default bot's model, `/api/link` (+ `/remote`, `/devices/:id/revoke`) for 連線, `/api/browser/status` + `/install`, `/api/telegram` — plus `apps/desktop/src/settings-system.ts` for 備份 (`backupNow` / `listBackups`, names only) and 關於 (version from `apps/desktop/package.json`, data folder, opening `<data>/logs` or the data folder through an injectable `openFolder`). Restore is deliberately not an endpoint.

### Log lines (`apps/desktop/src/log.ts`)

`log.error / warn / info / debug` write one timestamped line (ISO time, level) to stderr (error, warn) or stdout; `advanced.logLevel` sets how much is written and the 設定 screen changes it live. Core, Link and data-dir warnings go through it; the `pnpm desktop` banner is not a log line and always shows. As a service, stdout / stderr go to `<data>/logs/core.log`.

## P14 implementation notes (add-ons, conversation rules, offers)

Principle: what costs no extra model call is in the core for every bot (conversation rules, must-follow preferences, the offer ledger); what spends model usage on its own, or is useful to only a few bots, is a built-in **add-on** a bot turns on for itself, off by default, with a daily cap.

### Add-on framework (`core/src/addons/manifest.ts`, `service.ts`, `store/src/repos/addons.ts`, migration 17)

`ADDONS` is a static list in the program: 主動留意 (`proactive`, cost class `proactive`), 回覆檢查 (`reply-check`, `on_use`), and the P13 features 提前做 (`early-work`) and 小模型審 shell (`shell-review`) as adapters that read and write their original bot columns (no change of meaning, no migration for them). Nothing is loaded from outside the program and there are no third-party add-ons. A manifest has a 繁中 name and line, `costClass` (`none` / `on_use` / `proactive`), a zod settings schema where every field has a default, `requires` (`engine_completion`, `connected_app`) and default daily token / run caps. `AddonService` keeps the switch and settings in `bot_addons` (settings merged over the current ones and parsed whole; a stored value that no longer parses falls back to the defaults) and usage per local day in `addon_usage`. An add-on asks `allowance` before each run and `charge`s what it spent; past a cap it stops for the rest of the local day (`capped_at` is kept for that day) and `addon.capped` goes out once. Raising the cap the same day does not lift that day's cap. Turning an add-on off stops its schedule and clears its queued cards (kept, not deleted); turning it on starts from now and never catches up. API `apps/desktop/src/addons-api.ts`; UI: the bot editor's 擴充 tab (`ui/addons.ts`) and the phone bot sheet's 擴充 list (`app/addons.ts`).

### Conversation rules (`core/src/conversation-rules.ts`, `prompt.ts`)

Nine rules (answer first, one question, ask late, consequences before the irreversible, change direction after two refusals, at most one doable offer and none after a goodbye, no repeated offers, memory without show-off, adjust plans, match the tone), each with a made-up good and bad example, in a 繁中 and an English copy chosen from the bot's language. They are part of the stable prompt layer of router and thread turns, so the layer stays byte-identical per bot and the prompt cache keeps it.

### Must-follow preferences (`core/src/must-follow.ts`, `memory` extractors, migration 17)

`memories.applies_to` (`send_message`, `publish`, `purchase`, `booking`, `code`, `schedule`, `any`) is set by the rule and model extractors for instructions about a kind of action (寫信不要提到 X …); deadlines the person mentions become project memories with `due_at`; 別再提 X becomes a `suppress` preference for proactive offers. When a worker or the router is about to use a tool of that action class (draft tools included), the bot's visible memories for it (≤ 5 items, ≤ 200 tokens, outside the recall budget) go into that request as an `<alca:must-follow>` block, and the approval card lists them as 已套用.

### Offer ledger (`core/src/offers.ts`, `store/src/repos/offers.ts`)

A router reply whose last sentence offers to do something is recorded in `offers` (`source = chat_end`, category by keywords). The person's next message decides it with plain rules (好／可以 → accepted, 不用／先不 → declined, otherwise pending and ignored after 24 h). A decided offer is final (trigger). `offerStats` gives the per-category accept rate for 主動留意's scoring and its settings line; a conversation's declined offers go into the router's context so they are not offered again there. Events `offer.created` / `offer.updated`.

### 主動留意 (`core/src/addons/proactive.ts`, `proactive-sources.ts`, `proactive-pick.ts`)

Per bot with the add-on on, every `scanMinutes`: a scan with no model over the sources it may read — deadlines from conversation (memories with `due_at`), Alca's own state (failing routines, cards waiting more than 6 h, unused drafts) and, through the host, calendar and mail (subject, sender, date and preview only); nothing new → quiet, 0 tokens. One tool-less completion on the bot's engine turns the new evidence into at most 3 candidates (schema- and evidence-checked). Plain code scores them (timeliness 0.35, relevance 0.25, doable 0.2, smoothed accept rate 0.2; suppress, reused evidence or overdue → 0; threshold 0.55). The best one gets a read-only homework worker (only reads and search; anything else is refused before the gate) when the day's budget allows, else the candidate text is used. The card (好 / 先不用 / 別再提這類) is posted in the bot's own 主動留意 conversation and listed in the pending areas — the desktop card strip and the phone's 待處理 — within the quiet hours, the daily count and the minimum gap, else queued; past `due_at` it expires; unanswered for 48 h it is ignored. 好 starts an ordinary worker at the bot's level (sends, payments, deletes and posts still ask). It never sends anything itself.

### 回覆檢查 (`core/src/addons/reply-check.ts`)

A `TurnObserver`: after a completed router reply, one tool-less completion checks it (more than one question, asking what memory already has, offering what the bot cannot do, naming a memory's source, repeating a declined offer, breaking a must-follow instruction), plus two plain rules in code. On issues the reply is rewritten once by a tool-less rewrite prompt — not a rerun of the router turn. A rewrite that still breaks a plain rule, an error or the timeout (default 4 s) keeps the original. The check runs after the reply has been delivered, so the phone may already have the original; a rewrite replaces the stored message and goes out as `reply.revised`, and both surfaces swap the text and mark it 已修改. The check runs on the bot's router model unless the add-on's settings pick another of the bot's configured models (`EngineSet.modelChoices` / `forAddonModel`, `AgentSystemOptions.engines.addon`); a pick that can no longer be built falls back to the router engine. Usage counts against the add-on's daily cap.

## Worker harness implementation notes

Every worker the router dispatches runs under one of two **harnesses**, `coding` or `general` (`core/src/harness/kinds.ts`). A harness is a profile — tools, rules, budget, stop conditions (`core/src/harness/profiles.ts`) — on top of one shared outer layer.

```text
router (總機) ── worker_start {harness?, doneWhen, workdir, ownsPaths, checks, budget, handoffFrom}
   │
   ▼
OUTER LAYER — always Alca, engine-independent (core/src/agents/harness-run/*)
   dispatch contract · budget · gate · host verification · reviewer
   "what it did" from events · NEEDS_INPUT · ledger + restart reconcile
   │
   ├─ API key engine  → Alca's own loop + coding tools (core/src/harness/coding/*)
   │                    or general tools (core/src/harness/general/*, browser/src/general-tools.ts)
   └─ subscription CLI → the CLI's native loop and tools; permission requests go to Alca's gate
                         (Claude Code, Codex app-server, ACP)
```

### Outer layer (`core/src/agents/harness-run/*`, `core/src/harness/*`)

- **Dispatch contract** (`harness/dispatch.ts`, `harness/contract.ts`): `readHarnessDispatch` reads the harness fields of `worker_start`; `dispatchGrants` stores them on the worker. The worker reports through `report_result` (`status` done / partial / needs_input / blocked / unverified, `summary`, `changes`, `claims`, `proposal?`).
- **Outer turn loop** (`harness-run/run.ts`): `workers.ts` only calls it. After every turn `decideNext` (`harness-run/decide.ts`) runs the rules in order: stop → await → overflow → retry → budget → stall → pass-boundary compaction → verify → review → follow-up → remind → end. Each rule is one function with its own tests.
- **Budget** (`harness/kinds.ts`, `harness-run/tally.ts`): one step = one `tool.completed`, counted by the watchdog for every engine, CLIs included; tokens are booked when a usage event arrives. Defaults `HARNESS_DEFAULTS`: coding 120 steps / 3600 s, general 60 steps / 1800 s. Bot settings may lower them and a dispatch's `budget` may only lower them further; `passCap` (steps × 2) is a safety cap only.
- **Gate**: every write and command of a harness worker goes through the action gateway (`policy/src/gateway.ts`); shell-running tools are classified by their command (`policy/src/shell-tools.ts`, `classify.ts`, `dev-commands.ts`).
- **Host verification** (`harness-run/verify.ts`): check commands come from the dispatch's `checks`, then AGENTS.md / CLAUDE.md, then `package.json` / `pyproject` / `Cargo.toml` / `go.mod`. The host runs them in a bash session in the work folder; a verification is stale when a file changed after the last green run. Red output goes back to the model, at most 3 rounds, then the report is `unverified`. For CLI engines the host verifies after the turn and sends the result back into the same session as a follow-up. Rounds are written as `verify.started` / `verify.result` dispatch events.
- **Independent reviewer** (`harness-run/review.ts`): per bot, off by default (`reviewer` in the bot's harness JSON, `parseBotHarness`). A tool-less one-pass session reads the diff (coding) or the report and outward actions (general) against goal / doneWhen and answers `{met, gaps[]}`; gaps go back to the worker at most twice, then the report is `unverified`.
- **"What it did" from events** (`harness/actions.ts`, `harness-run/report.ts`): `HarnessActions` is computed from events (files changed, commands run, pages opened, connections used, outward actions); `formatWorkerReport` puts it next to the worker's own words for the router.
- **NEEDS_INPUT** (`harness/needs-input.ts`, `harness-run/waits.ts`, `agents/router-answer.ts`): 1–3 questions, recommended option first, `person_only` flags. The router answers with `worker_answer` only when the question is not person-only and the bot's effective level allows; the person answers from the worker panel. Text questions expire after 72 h; questions with options never expire. A continuation worker carries the same `dispatchId`.
- **Ledger and restart** (`harness-run/ledger.ts`, `reconcile.ts`, `store/src/repos/dispatches.ts`, migration 18): `dispatches` with a writer fence (`active_run_id`), append-only `dispatch_events`, `harness_waits` claimed by compare-and-set. `reconcile` after `WorkerSupervisor.recover`: outward actions → `interrupted_after_outward` (never redone), already requeued once → failed, otherwise requeued once.

### Inner layer

- **API-key engines** run Alca's own loop. Coding gets `read`, `edit`, `write`, `apply_patch`, `grep`, `glob`, `bash`, `bash_poll`, `bash_input`, `bash_kill`, `todo` (`harness/coding/tools/*`, wired by `harness-run/coding.ts`; `ownCodingLoop` holds only for a coding dispatch on an engine that does not own its tool loop). General gets the lazy tool catalog (`harness/general/lazy.ts`), `web_fetch` (`harness/general/web-fetch.ts`), `await_event` / `list_waits` (`harness/general/waits.ts`) and the browser tools including `browser_script` (`browser/src/general-tools.ts`, `browser/src/sandbox.ts`).
- **Subscription CLIs** keep their native loop. Claude Code (`core/src/agents/claude.ts`): one engine instance per harness with a fixed tool list; coding keeps native Edit / Write / Bash, each asking the permission tool; general removes native shell and writes with `--disallowedTools` and reads the CLI's init message back; both carry `--max-turns` as a backstop. Codex (`engines/src/codex/app-server/{process,rpc,map,engine}.ts`): JSON-RPC over stdio, coding at `workspace-write` + `approvalPolicy: "untrusted"` (on-request at 完全授權), general and reviewer `read-only` + `never`; `exec --json` stays for read-only use. ACP (`engines/src/acp/engine.ts`): coding in the agent's asking mode, general with `denyKinds` and `strictMode`. Desktop picks the instance with `EngineSet.forHarness(botId, kind)` (`apps/desktop/src/engines.ts`).

### Capability matrix and `checkHarnessFit` (`engines/src/harness-matrix.ts`)

Each engine instance declares `loop` (own / cli), `writes` (native / host_tools / none), `asksBeforeWrite` and `asksBeforeExec` (every / some / never), `nativeStepCap`, `interrupt`, `usageStreaming`, `resume`; `HARNESS_MATRIX` lists the rows (`api`, `claudeCoding`, `claudeGeneral`, `codexExec`, `codexAppServerCoding`, `codexAppServerOnRequest`, `codexAppServerReadOnly`, `acpCoding`, `acpGeneral`, `acpAtLevel`). An undeclared tool-owning engine is assumed to ask only sometimes. `checkHarnessFit`:

- coding: Alca's own loop, or a CLI whose native writes and commands all ask; an engine that cannot write is refused. At 完全授權 a CLI that asks only sometimes fits too. At 完全授權 every coding fit — own loop, Claude Code, ACP, Codex — keeps a git snapshot before every turn where it can (`snapshotEachTurn`), since the gate clears every write and command unasked there; the snapshot is best effort (11-05): a folder that is not git, or a snapshot that fails, still runs, and the ledger records `snapshot.skipped` (`not_git` once per worker, `snapshot_failed` per turn) for the worker panel.
- general: no native write or command may run unasked.

`WorkerSupervisor.start` checks the fit (`harness-run/full-access.ts` `dispatchFit`) before any worker or CLI exists; a refusal goes back to the router as `harness.engine_unfit` with a sentence. The router never picks an engine.

### Harness choice (`harness/dispatch.ts`, `agents/router.ts`)

A named `harness` wins; otherwise the bot's default (bot settings) → the heuristic (`guessHarness`: a `workdir`, or a goal about code, files or a repo → coding) → general. Only a heuristic guess falls back to general when the engine cannot do coding; a named or bot-set harness is refused. `HARNESS_CHOICE_RULES` (繁中 and English) sit in the router's stable prompt layer.

### LoopGuard (`core/src/loop-guard.ts`)

The one set of stop rules, judged on "call signature + result hash": `repeated_failure` (only consecutive failures; a success resets), `ab_cycle`, `no_progress`. A poll of a background process whose output changed is never a repeat; a known check command that comes back red is a normal failure. Attended runs are warned from the 3rd repeat; unattended runs stop at the 6th. Separately, three stalled turns in a row (tools called, no non-contract tool succeeded, no file changed) end the dispatch as partial (`EndWhy` `stalled`).

### Compaction (`core/src/harness/context.ts`, `harness-run/compact.ts`)

API engines only (CLIs compact themselves). Threshold `window − max(15 % · window, 16k)`, keep `clamp(20 % · window, 8k, 20k)` (`TOKENS`). Around 70 % of the threshold (`PREPARE_SHARE`) a handover summary is written between turns ahead of time and used at compaction. At a pass boundary over the threshold the model is asked to write its progress and `rulePassCompact` compacts after the turn. Before compacting the todo snapshot, changed files and the outward ledger are flushed; two ineffective compactions in a row stop and report.

### Snapshots (`core/src/harness/git-snapshots.ts`, `store/src/repos/git-snapshots.ts`, migration 19)

Before every coding turn at 完全授權 the host keeps a hidden ref `refs/alca/snapshots/<dispatch>/<n>`; a turn that cannot get one still starts (11-05) and the dispatch ledger records `snapshot.skipped` with `not_git` (once per worker) or `snapshot_failed` (with the git error); `harnessView` turns that into `snapshotSkipped` for the panels. At most 20 per repository (oldest first out), kept 7 days after the dispatch settled; the sweep runs at most hourly from `AgentSystem.sweep` and `git gc` at most once a day. `AgentSystem.snapshotList` / `snapshotRestore` / `snapshotPurge` back the desktop routes; a restore first keeps the current state as one more snapshot. The per-file undo journal of P13 (`workspace/journal.ts`) is separate and unchanged.

### The core's keys and the data key (next round D1)

`apps/desktop/src/data-dir.ts` `openDataDir(dir, { keySource? })` is async: it makes the folder's **one** `Vault` (`@alca/os`; key source `defaultKeySource`, i.e. `LazyKeySource` over the macOS Keychain / Secret Service / 0600 `vault.key`), loads the core's secrets with `loadCoreSecrets(root, vault)` (`core-secrets.ts`), and returns `vault` with the rest; `createConnectors({ vault })` and everything after it use that instance. `loadCoreSecrets` reads the token from `secrets.json` and `core.linkIdentity` / `core.vapidKey` from the vault, moving them out of an older `secrets.json` (one `setMany`, then `readBack` from the file, then `secrets.json` and its `.bak` rewritten with only the token and `core.secretsIn: "vault"`). `Vault.keyStatus()` (`{ where, degraded, reason?, forced? }`) is what the start log and `alca secrets status` print. `secrets-cli.ts` has `status`, `export`, `import`, `reset`.

**Getting the data key (for Phase F2).** From `@alca/os` (`packages/os/src/data-key.ts`), all taking the folder's vault (`dir.vault`, any `SecretStore`):

| Call                                         | What it does                                                                                                                                                  |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ensureDataKey(store)` → `{ ring, created }` | The ring, making key 1 (32 random bytes) the first time; the new entry is stored and read back from the vault file before it is returned. Call once at start. |
| `getDataKey(store)` → `ring \| undefined`    | Read only; never creates (for restore checks, `db verify`, anything that must not mint a key the database was not sealed with).                               |
| `rotateDataKey(store)` → `ring`              | Adds key `n+1` and makes it current; older keys stay in the ring.                                                                                             |
| `deriveSubkey(ring.key, label, length = 32)` | HKDF-SHA256 sub-key per purpose, e.g. `deriveSubkey(ring.key, "alca fts")` for R7.4's keyed FTS tokens.                                                       |

`ring.current` is the key id to write into each sealed value (`k`), `ring.key` its key, `ring.keyFor(k)` the key for an id read from a row (undefined → that row was sealed with a key this ring never had: stop, do not re-seal), `ring.ids` every id. The entry is `core.dbKey` (`DATA_KEY_NAME`), stored as `{"v":1,"current":n,"keys":{"1":"<base64>",…}}`. Errors: `DataKeyError` for a malformed entry (never replaced by a new key), the vault's own `VaultError` when the vault does not open (its keychain item gone) — never a fresh key in either case. Because the name starts with `core.`, `alca secrets export` carries it and `alca secrets reset` leaves it. Its protection is the vault key's: when `vault.keyStatus().degraded` is true the key sits next to the database in effect, and the settings page should say so (R7.5 step 1).
