# Security model

Covers Alca Link, the phone PWA and `hands`; memory; connected apps; the team; push, the service, the desktop shell and the installers; Google sign-in; the browser; add-ons; the worker harness; the OS sandbox; data retention, the vault and column encryption; web search and MCP servers.

**Found a vulnerability?** Report it privately: [SECURITY.md § Reporting a vulnerability](../SECURITY.md#reporting-a-vulnerability). Cryptography and its review status: [CRYPTO.md](CRYPTO.md).

What Alca Link protects, from whom, and what it does not. Wire format: [PROTOCOL.md § Alca Link](PROTOCOL.md#alca-link-p4).

## Assets

- The core's state (threads, memory, browser Spaces, approvals) and its ability to act: pay, send, delete, publish, run commands on paired machines.
- Device identity keys: the core's (in the sealed vault since next round D1 — the vault key in the OS keychain, or degraded to a 0600 `vault.key`; older folders move it out of `secrets.json` on first start), each phone's (non-extractable WebCrypto key in IndexedDB), each hands daemon's (`~/.alca-hands/device.json`, 0600).
- The person's yes on an approval card.

## Main decisions

- **The PWA host is trusted code.** The page's JavaScript holds the phone's key handle and sees decrypted messages. Whoever serves `index.html` / `app/*.js` / `sw.js` (the relay with `--pwa`, or the `--pwa-url` host) can ship a page that misuses them — end-to-end encryption protects against the _transport_, not against the code you run. Serve the PWA yourself, from an origin you control, over TLS; the service worker pins the cached version until a new build is fetched. Pairing material sits in the URL fragment (`#pair=…&fp=…`), which browsers do not send to the server.
- **Pairing is authenticated by the short code, once.** SPAKE2 on a 6-digit secret, since G1 exactly RFC 9382 with key confirmation (PAKE v2): the phone proves it knows the code before the computer sends anything keyed by the exchange, and the computer proves it before the phone sends its key. An active relay gets one online guess per code: once a phone has sent its share, any failure burns the code on the computer and the relay and a new code is needed (a connection that drops before that may retry, up to `pairingMaxAttempts`); codes are single use with a 120 s default TTL and claims are rate-limited per address. A passive relay records nothing it can test a code against. A computer accepts PAKE v2 only, and **PAKE v1 is removed** (no setting re-enables it): a device that offers only v1 (anything from `v0.2.0`) gets `upgrade_required` before any PAKE runs, nothing is stored, it is told to update and pair again, and the refusal is audited (`detail.refused = "pake_v1"`). A phone sends only a v2 share and stops with `downgrade` if a computer answers with v1, so there is no downgrade path left to strip into. A QR code carries `pk=2`, the version list kept for later negotiation. The cryptography is described, with its open questions, in [CRYPTO.md](CRYPTO.md); it still needs an external review. The device additionally checks the core's key fingerprint from the QR when it has one; the 4×4 hex safety number on both screens lets a person compare after typing a code.
- **Every session is signed against pinned keys** with fresh ephemerals (forward secrecy; a recorded handshake cannot be replayed). Frames carry a strict per-direction counter: a replayed, dropped, reordered or modified frame closes the channel.
- **The core has no inbound port.** It connects out to the relay and proves it owns its mailbox with a signed challenge; the optional LAN listener speaks only the Link handshake.
- **Policy stays on the core.** Phone answers and hands calls go through the same gateway, audit row (written before execution) and always-confirm classes as anything else; a denied hands call never leaves the core. Phone actions are recorded as `user:device:<id>`.
- **Revocation is permanent**: the device row is kept, its key can never change, live sessions end at once and the device stops reconnecting.

## Memory and learning (P5)

What Alca remembers is personal data about the person; these are the rules it keeps and the limits it has.

**Where it lives.** Only in `state.sqlite` on the core's computer (tables `memories`, `skills`, `skill_versions`, `memory_tombstones`, `memory_meta`). No embedding model ships and memory search makes no network call; if a local embedder is plugged in, its vectors sit in the same file. A phone reads memory only over sealed Link frames and only with the `chat` scope; the learning channel carries ids, kinds and skill names, never a memory's text. Deciding on a skill needs `approve`. Export writes a JSON file **the person** then holds: once shared or synced, it is outside Alca's control.

**What it refuses to keep.** A candidate memory that contains a secret (private keys, API tokens, JWTs, bearer headers, credentials or secret parameters in URLs, labelled passwords, card numbers passing Luhn, Taiwanese national ids, high-entropy strings) is dropped whole, not masked and kept; secret values in learned skill steps are replaced by a marker. The filter errs on the side of flagging and is pattern-based: a secret in an unusual shape can get through, so do not rely on it as a vault.

**What a skill can do.** Nothing a person could not already approve. A skill is text handed to a worker; every step still goes through the policy gateway and its audit row, and payment / send / delete / publish ask every time whatever the permission level (tested under 自主 with a saved checkout skill in real Chromium). The router can pass a worker only the bot's own active skill and memory that bot may read (checked by the core).

**Inferred vs said.** Inferences are labelled as such everywhere they appear (UI, recall tags in the model's context) with a confidence; an inference never replaces something the person said or confirmed (a service rule; a store trigger also keeps a confirmed item from going back to inferred), and recalled memory is fenced as data in the user message, not instructions.

**忘記 (forget)** deletes every version of the item (a hard `DELETE`; the FTS index entries are removed by trigger) and writes a **tombstone** so the same thing is not learned again. A tombstone is not the text: it is an HMAC-SHA-256 digest of the normalized text plus 8-hex-character HMAC shingles of its content tokens (CJK bigrams, Latin words), keyed by a random per-store key in `memory_meta`. Limits, stated plainly:

- **Dictionary test.** Someone holding the store file **and** therefore its key can hash a dictionary of candidate words or bigrams and test which ones a tombstone contains. Shingles are short and unordered, so this leaks _which common tokens_ were in a forgotten item, not reliably the sentence; a short or predictable item (a name, a place) can be confirmed by guessing it whole against the digest. The key lives next to the data, so tombstones protect against casual reading of the file, not against someone with the file. 「讓 Alca 可以重新學習」 deletes all tombstones (and with them this residue) at the cost of letting Alca learn those things again.
- **忘記 does not delete the original chat messages.** The words the person typed stay in the thread (`messages`) and in the run log (`run_events`; append-only by trigger, **not** hash-chained — only `audit_log` is), along with the assistant's replies that may repeat them. To remove those, delete the conversation: its content is really deleted (§ Deleting a conversation, export and import), or delete the data directory. Remote engines have also seen the text: a Claude Code session keeps its own transcript under the CLI's directory (outside Alca's reach, see that section), and recalled memory was sent to the model in earlier turns.
- **Storage residue.** Every writable connection runs with `secure_delete = ON` (deleted content is zeroed in its page), the hourly sweep checkpoints the WAL with `TRUNCATE`, and free pages are given back weekly (`auto_vacuum = INCREMENTAL`, switched once at the first start of this version for files up to 500 MB). Backups keep whatever they captured unless a delete scrubs them: deleting a conversation also rewrites every backup file by default (「也從備份裡清除」); with that unticked it can stay in the daily backups for up to 7 days. Copies of the data directory, file-system snapshots (APFS, Time Machine) and SSD wear levelling are outside SQLite's reach. Use full-disk encryption on the computer that runs the core.
- An exported JSON taken before the forget still contains the item.

## Connected apps and routines (P6)

**Where the secrets are.** The person's **OAuth tokens for their apps live at Composio**, not on this computer: Alca calls Composio's API with the person's own Composio key, and Composio calls Gmail, GitHub, … on their behalf. The person accepted that trade (no token handling or refresh on the core, at the cost of trusting Composio with app access); someone holding the Composio key can use every connected account, so treat it like a password. The key itself is entered once on the desktop, checked with Composio, and sealed in `vault.json` (AES-256-GCM, 0600) in the data directory; it is never returned by the API (status says only whether it is set, plus `••••` and the last four characters on the desktop), never sent over Link (the phone's status drops even the preview, and there is no key op), never put in a prompt or a tool result, and only host code reads it. The vault's own key comes from the macOS keychain, the freedesktop Secret Service, or a 0600 `vault.key` file next to the vault (the fallback, and what tests use): with the file, anyone who can read the data directory can open the vault — use full-disk encryption.

**macOS Keychain: the key goes over stdin.** When Alca stores the vault key the first time it runs `security -i` and writes the `add-generic-password -U … -w <key>` command on the tool's stdin, so the key never appears in its command line or in a process listing (`ps`); the key is then read back to confirm the Keychain took it (interactive mode can exit 0 after refusing a command). Reading it (`find-generic-password -w`) prints it on the tool's stdout, which only Alca reads. The Secret Service path passes the value on stdin too. A local process that runs as you can still ask the Keychain itself (macOS may prompt) or read the data directory, so the keychain is not a defence against malware running as the same user.

**What the agent may do with an account.** Per account and per bot: nothing, read tools only, or act. A tool's class comes from its slug and Composio's tags, and anything unclear counts as `send` (fail closed); `inspect` may raise a declared read to a changing class, never lower it. Send / publish / delete / payment ask every time through the same gateway and audit row, with the account label and the recipient on the card, and stop at a per-bot daily quota (payment defaults to 0 = never through a connected app). App results are cut to a budget and fenced as untrusted data (`<alca:app … trust="untrusted">`), so text in an email is never read as an instruction. A draft prepared ahead (提前做) is only stored; using it is a new request in the chat that goes through the card again.

**Routines.** A check reads with plain code; only new items reach the model, and at most `maxAiRunsPerDay` AI runs per bot per day. A read failure keeps the cursor (nothing is skipped silently) and backs off; the cursor moves in the same transaction that saves the result.

**Relay webhook mailboxes.** App events reach a core with no inbound port through a mailbox on the person's own relay: Composio POSTs to `/v0/hooks/<id>`, the core pulls with a token whose SHA-256 the relay stores, and the core checks Composio's HMAC signature and a webhook-id duplicate guard before an event can fire anything — so the relay cannot forge or replay an event. It **can read them**: event bodies (an email's subject, sender and preview) are plaintext to the relay, held in memory for up to a day, bounded in count and size. With `--hooks-file` they are also written to that file (0600) until pulled; without it a relay restart drops undelivered events (the core notices the new mailbox and resets its cursor, so later events still arrive). Self-host the relay for this reason. On the **Workers relay** (review M3) each mailbox is its own Durable Object with the same protocol and limits (500 events of 256 KiB, a day; an idle empty mailbox deletes itself after a week), and the events sit in Durable Object storage until pulled — readable by whoever runs that Cloudflare account, so the same advice applies.

**Relay connection limits (review M1, M2).** Behind `--trust-proxy` the Node relay keys its rate limits by the rightmost `X-Forwarded-For` entry (the one the proxy appended; `--trust-proxy-hops N` for N proxies), not the leftmost, which the client writes itself. Both relays close a socket that does not say who it is within 10 s (`helloTimeoutSec`) or sends nothing for 30 min (`idleTimeoutSec`; cores ping every 15 min, phones every 25 s), allow 32 sockets per address and a total cap (Node 20 000, Worker `MAX_SOCKETS` 5000), budget each connection to 1 MiB/s with an 8 MiB burst on top of 300 messages/s, and let one address hold at most 8 of a core's 64 channels, so a stranger who knows a mailbox id cannot take all of them. The Workers relay keeps every relay socket in one Durable Object (a single-threaded bottleneck and point of failure past a few thousand devices); its `/healthz` is public and reports counts and configuration warnings, never accounts or mailboxes. Set `ALLOWED_ORIGINS` (and `RELAY_MODE=production`) on an official deployment so other websites cannot open relay sockets from a visitor's browser.

**Phone site CSP (review L5).** `vercel.json` and the Node relay send a CSP that allows any `wss:` host in `connect-src` (the source names no deployment). A build that knows its relay adds a `<meta>` CSP narrowing `connect-src` to the site, that relay, `wss://*.ts.net` and Google Identity Services (`ALCA_CSP_CONNECT_EXTRA` adds origins, `ALCA_CSP_CONNECT=open` turns it off); the browser enforces both.

## Team (P7)

**A delegation narrows, it never widens.** When a bot asks or hands work to a teammate, the teammate's peer conversation runs under two narrowed rules, both checked by the core on every call:

- **Approval level**: the strictest level of every bot in the chain (if any of them is 每步確認, every step asks), whatever the teammate's own level. Payment / send / delete / publish ask every time regardless.
- **Connected apps**: only the accounts every bot of the chain may use, at the lowest access any of them has (`ConnectorService.usable(botId, threadId)`). A teammate that may act on 工作 and 個人, asked by a bot that may only read 工作, sees only 工作, read-only, in that conversation.

Cards raised in a peer conversation are shown in the person's conversation the chain started from, so the person answers them where they are. The team rule (`ask_delegate` by default) puts a card before a delegation; depth, loops and the open-request cap refuse rather than queue, and every request and step is recorded (`peer_requests`, append-only `peer_events`).

**Not narrowed: a teammate's browser profile and memory mode.** The teammate works with its **own** browser profile and its **own** memory settings, not the asking bot's. So an isolated bot that asks a teammate on the shared profile gets work done in that teammate's browser — with the shared profile's logged-in sessions — and a bot with memory `off` that asks a teammate with team memory gets an answer informed by what that teammate may read. The isolation of a bot is a boundary for what **it** opens, not for what its teammates do on its behalf. If a bot's isolation matters, keep its teammates isolated too, or set the team rule to `都先問我` so every request needs your yes.

**Model services.** A key for OpenRouter, Gemini or another OpenAI-compatible service is kept in the local vault (`engine:<id>`, same vault as P6), read at call time and sent only in the request header; it is never returned by the API, never sent over Link (the phone sees engine names only), never put in a prompt, a tool result or an error message. A remote service must use https; http is accepted on loopback only (Ollama, LM Studio). Whatever service a bot uses sees that bot's conversation and the tool results in it, like any engine.

## Push, service, shell and installer (P8)

**A push carries no content.** The encrypted payload (RFC 8291 `aes128gcm`, keys from the phone's subscription) is exactly `{v, t, id}`: a version, a kind (`approval`, `question`, `handoff` or `test`) and an opaque id. No title, amount, name, recipient or text ever goes to Apple's, Google's, Mozilla's or Microsoft's push service; the phone shows a fixed local sentence (等你決定 — 有一件事要你點頭。) and, once opened, fetches the details over the end-to-end Link session. A push service still learns **that** and **when** something happened for that phone (timing metadata), and `Urgency` / `TTL` headers. Tapping a notification only opens the app at `#open=<kind>:<id>`; approving still needs the sealed session and the device's `approve` scope, so a forged push cannot approve anything.

**The VAPID key stays local.** The ES256 key pair (RFC 8292) is generated on the computer on first start and kept in the sealed vault next to the Link identity (`secrets.json` before next round D1); only its public half is given to phones. The JWT `sub` contact is `$ALCA_PUSH_CONTACT`, else settings `engineering.push.contact` (default `mailto:admin@example.com`; set your own). There is no Alca push server: the core POSTs to the endpoint itself.

**Only known push services are contacted.** A subscription endpoint must be https on `fcm.googleapis.com`, `android.googleapis.com`, `updates.push.services.mozilla.com`, `*.push.apple.com` or `*.notify.windows.com`; anything else is refused before a request is made (tests pass an explicit allow hook for a loopback mock). This keeps a paired phone from turning the core into a request-sender to arbitrary hosts. Subscriptions belong to one paired device and are deleted with its revoke; 404 / 410 from the service forgets them; the delivery log records outcome and status only.

**Service and shell.** `alca service` runs the core as the logged-in user (LaunchAgent / systemd `--user` / a per-user scheduled task), never as root, binding loopback only as before. The desktop shell's own splash gets Tauri's `core:default` capability only; the core's page, loaded from `http://127.0.0.1:<port>`, gets **no** Tauri IPC, so a bug in the core's UI cannot reach native APIs through the shell. The local token travels to the window in the URL fragment (never sent in a request) and is read from `secrets.json`; since review 2026-11-04b S2.2 the token alone cannot approve (see § Review 2026-11-04b), and the shell hands its window a one-time launch code over the core's stdin. `alca://` links only bring the window forward or open the 手機 dialog; they carry no data into the core.

**Installer.** `scripts/install.sh` downloads over https only (curl with TLS 1.2 or later), refuses `http://`, keeps `~/.alca` at 0700 and never touches data files when it replaces `app/`. It installs a tarball only when its SHA-256 matches a checksum it was given: the release's `.sha256`, `--sha256 <hex>`, or a `<file>.sha256` next to a local `--tarball`; with none of these it **refuses** (it used to install a `--tarball https://…` silently when the `.sha256` could not be fetched) unless you pass `--insecure`. `--attestation` also runs `gh attestation verify` against the release's build provenance. A checksum from the same release page protects against corruption, not against a compromised release; the provenance attestation (Sigstore, written by `release.yml`) ties a file to this repository's workflow run, but GitHub offers it free only for **public** repositories, so a private repo's releases have none. Builds are **unsigned** for now (macOS notarization and Windows Authenticode need the owner's developer accounts), so verify the source of what you install.

**Release workflow (review H4).** Every action in `.github/workflows/` is pinned by commit SHA (with the version in a comment; `.github/dependabot.yml` proposes updates weekly). The Tauri CLI is a devDependency of `apps/desktop-shell` at an exact version in `pnpm-lock.yaml` (it was `npx @tauri-apps/cli@2`, a floating major). The `APPLE_*` secrets are no longer job-level env: the certificate and its password are in the env of the keychain-import step only, the signing identity in the Node-signing step, and the identity + Apple ID / app-specific password / team in the `tauri build` step (which runs `cargo build`, so those three still reach build scripts there — the certificate does not); `pnpm install`, `cargo test` and the core bundling see none. The tag must equal the version every `package.json` / `tauri.conf.json` / `Cargo.toml` carries (`scripts/check-versions.ts`). The workflow has still never run (no tag yet).

## Stable address, reconnect, Codex and model extraction (P9)

**Pairing codes allow 5 tries.** A wrong code no longer burns the code at once: the core reopens the nameplate (`nameplate.reopen`) so a typo can be fixed, and the relay counts every claim on it — 5 in all (`maxClaimsPerNameplate`), one claimer at a time; success or the 5th failure burns it on both sides, and the 120 s TTL and the per-address claim rate limit still apply. An online guess is one SPAKE2 run against a 6-digit secret, so 5 tries give an attacker at most 5 in 10⁶ per code, and a successful impostor still shows up in the device list with its own safety number.

**The mailbox id is derived, not assigned.** The mailbox = the first 128 bits of SHA-256 of the core's long-term Link public key (22 base64url characters). It is stable across core and relay restarts and relay moves, so phones never re-pair for those; it is not a secret (anyone who has it can see whether the core is online, via `probe`, and dial it), but dialing gets nothing without a paired device key, and only the holder of the core key can listen on it (signed challenge). A new Link key — a fresh data dir — is a new mailbox and needs new pairings, by design.

**`probe` is one bit.** It answers whether a mailbox is registered and opens no channel; it shares the per-address dial limit. The core uses it on itself (every 15 min, with a relay ping) to spot a half-open socket or a relay that lost it, and re-registers.

**Endpoints only move inside a sealed session.** A new relay or direct address reaches a phone in `ready` or a sealed `endpoints` event from the pinned core, never from the relay or a page; a forged address can at most make a phone fail to connect, since every path still runs the signed session handshake against the pinned key. `link.json` (0600) holds addresses only; relay URLs must be https / wss (http / ws only to loopback), with no credentials in the URL.

**Codex CLI.** The router, general workers and the reviewer run Codex with its own sandbox read-only and its own approvals off (`never`); a coding worker (worker harness) runs `codex app-server` with `workspace-write` and `approvalPolicy: "untrusted"` (`on-request` at 完全授權; see § Worker harness and ROADMAP's known gaps). In the read-only case Codex cannot change files by itself (it can still run commands inside that read-only sandbox, which Alca sees only afterwards; see § Review 2026-11-04b); anything with an effect goes through Alca's host tools over MCP, i.e. inspect → policy gateway → audit → card, like every engine. The MCP bridge token is written to a 0600 file (`ALCA_BRIDGE_FILE`) and never appears on a command line or in `ps`. The person's Codex login stays Codex's; Alca never reads it.

**Model-based memory extraction is narrow by construction.** It runs in a separate conversation with no tools (every permission request denied, every tool call refused), sees only this turn, and may propose at most three items; one counts only when its quote is a verbatim substring of the person's own words in that turn (so the model cannot put words in the person's mouth or learn from the assistant's text or tool results), with a known kind and a short body. Items are always `inferred` with confidence ≤ 0.9, and the memory service still applies the secret filter, the 忘記 tombstones and confirmed-wins. It is off unless chosen per bot; the turn's text does go to that bot's engine a second time.

**Smoke tests** (`pnpm smoke`) read keys only from env vars set for that run, are never part of `pnpm test` or CI, and make read-only or plain chat calls; a failing call's message is checked not to contain the key.

**Design limits (P9).** The relay still sees metadata (which device dials which mailbox, when), and a mailbox id plus `probe` tells anyone holding it whether that computer is online. A direct (Tailscale / LAN) address is as private as your tailnet or LAN. Builds are unsigned unless the owner's `APPLE_*` secrets are set (macOS signing + notarization are wired into the release workflow; Windows Authenticode is not), and the release workflow has not run yet. The bundled Node is the official nodejs.org build, checked against that release's `SHASUMS256.txt` — which protects against corruption, not against a compromised nodejs.org; the bundled core is unpacked into the data dir with the user's rights, like `install.sh` (see [ROADMAP.md](ROADMAP.md)).

## Google sign-in and new devices (P10)

**What the Google sign-in protects.** It decides **who may find and knock on a computer**: the relay lists a computer only to someone holding a valid Google ID token for the account that registered it, and opens a `connect` channel (the only way to put an approval sheet on the computer's screen) only for that account. A stranger who knows a mailbox id cannot make the computer show a sheet; the per-address and per-account limits keep someone with the account from flooding it. It is also what lets the phone site skip pairing codes.

**What it does not protect.** Google sign-in is **not** what keeps the conversation private, and it does not make the phone trusted. The relay sees the token (and so, for that moment, the account's `sub` and email claims) and could lie about which computers exist or which key a computer has. So (P12):

- **The code on the phone authenticates both ends.** The phone shows a fresh, uniform 6-digit code; the person types it on the computer. It is the password of a SPAKE2 run (PAKE v2 since G1, the same construction as pairing codes: the phone's confirmation first, the computer's before the phone sends anything sealed), and each long-term key signs the PAKE transcript inside the channel that transcript keys. A relay without the code gets one online guess per try and has nothing to test codes against offline, and can get its key accepted by **neither** side: the computer stores a device only after the phone's confirmation and its sealed, signed frame, and the phone accepts a computer only after its confirmation, its sealed `enroll.done`, its signature, that its key owns the listed mailbox, and the listed fingerprint. A code is never tried twice: after a wrong try the phone shows a new code (an old phone page that speaks only v1 is refused `upgrade_required` before the computer asks for a code). 5 tries and 5 minutes per sheet. (Tested: right code; a typo then the right one; five wrong codes lock both sides with nothing stored; expiry; a relay in the middle with its own key fails on both sides; a swapped PAKE share; a key that does not own the listed mailbox.) This closes P10's open limit, where the phone trusted the computer's `enroll.done` without checking anything the person confirmed.
- **After the code nothing depends on Google.** The phone reconnects with its own key through the signed session handshake against the pinned computer key, exactly like a paired phone, with no sheet and no code. Signing out of Google, or the relay forgetting the account, does not end a trusted device; **revoke it in 手機與裝置** for that. Conversely a stolen Google account alone gets no session: it can put a sheet on the computer, which the person cancels (they have no code on a phone of theirs to type).
- **Tokens are not kept.** The relay verifies a token and keeps only the HMAC account key; the computer hands its ID token to the relay once (`computer.register`) and keeps only the email for display in `link.json`; the phone keeps the token in memory (and, with the full-page fallback, in the URL fragment until it is read and cleared).

**What the relay stores.** Only `HMAC-SHA-256(relay secret, sub) → [mailbox, computer name, key fingerprint, registered at, last seen]` (`--accounts-file`, 0600, or Durable Object storage). No `sub`, no email, no token. Someone with the file but not the secret cannot tell whose computers they are; someone with both can test a candidate `sub`. The computer **name** is visible to the relay (it is in the list); pick one that says nothing you mind. The relay secret is `$ALCA_RELAY_SECRET` or a generated 0600 `<accounts-file>.key` (Node) or a Wrangler secret (Worker), never in the repo.

**The computer's sign-in (P12): through the phone site, no client secret.** The computer listens once on `127.0.0.1` (random port) and opens `<site>/computer-signin?state=…&port=…` in the default browser (`open` / `xdg-open`). The site signs in with its own Web client (OIDC implicit) with `nonce = SHA-256(label ‖ state)` and Google's `state = "c." ‖ state`; on return it checks the state against what it stored for this tab, the nonce and the port range, then navigates top level to `http://127.0.0.1:<port>/google-callback#id_token=…`. The fragment never reaches a server; the callback page (its one script pinned by a CSP hash) posts it back to the listener, which accepts only its own origin, compares the state in constant time, checks the nonce, `aud` and `exp`, and ignores anything else (a stray or forged request does not end the sign-in). The relay verifies Google's signature and that `aud` is the site's client. What this trusts: the site's code (as for phones, whoever serves it could log the token in transit — a token that only lists and registers computers, and cannot get a key accepted without the phone's code); and the browser on this computer. The state is on the `open` command line for an instant (other local processes can list it); one that races to post a token of its own Google account only gets this computer listed under that account — 手機與裝置 shows which account — and a phone there still needs the code the person types on this computer. **Self-host alternative:** a Desktop OAuth client (installed-app flow per RFC 8252: loopback, PKCE S256, `state`; its "secret" is not confidential per Google's installed-app guidance and sits in `config.json`); it is used when `engineering.google.clientId` is set.

**Official endpoints are not secrets and not in the source.** The relay URL, site URL and Web client ID come from a release's build variables into a gitignored `official-config.json` (or the same names as environment variables, or a site's public `config.json`); `scripts/check-deploy-values.ts` keeps them out of the repository. 連線 settings override them; nothing in the code prefers them.

**The phone site.** Google Identity Services (its script, style and iframe from `accounts.google.com/gsi/`) is the only third party the site's CSP allows; it runs in the page, so — like the PWA host itself — it is trusted code there. The Web client ID is public by design; there is no secret on the site. COOP is `same-origin-allow-popups` so the sign-in pop-up can answer. The full-page fallback uses the OIDC implicit flow with a nonce kept in `sessionStorage` and checked on return.

**Design limits (P10).** The relay learns which account owns which computers (as a keyed hash), when they are online, and when someone lists or connects. Moving the computer to another relay drops its listing (enable it again there). One Durable Object serves the whole Worker relay (simple, not sharded). Not run against the real Google endpoints, on a real iPhone Home Screen app (whether the GIS pop-up returns there is the reason for the full-page fallback), or on Vercel / Cloudflare.

## Telegram reply channel (P13)

**What it can do.** Talk to one conversation of the chosen bot per allowed chat, as the person (`initiator user:telegram:<chat id>`), at that bot's approval level. **It cannot answer a card.** There is no Telegram path to `answerApproval` or to a question; payment / send / delete / publish, and every other card, are answered on the computer or a device paired over Alca Link. ## Alca Browser: first-run download, network-layer gate, Chrome cookie import (P13)

**First-run Chromium download.** When no Chromium is found (`--chromium`, `$ALCA_CHROMIUM`, `<data-dir>/browser/bin`, system paths) the desktop app fetches Chrome for Testing for this OS and CPU (`mac-arm64`, `mac-x64`, `linux64`, `linux-arm64`, `win64`, `win32`) from Google's public index `googlechromelabs.github.io/chrome-for-testing/last-known-good-versions-with-downloads.json` (Stable). Only `https` URLs from the index are accepted. The zip is downloaded to `<data-dir>/browser/bin/.download/` with resume (`Range` + `If-Range` on the ETag) and up to three retries with back-off, then checked against the server's `x-goog-hash` (MD5, and CRC32C) — the size when the server gives no hash — and unpacked by Alca's own zip reader, which checks every entry's CRC-32 and size, keeps modes and symlinks, and refuses absolute paths, `..`, and links that point outside the destination. The browser lives only under the Alca data dir; nothing is installed system-wide. **Trust:** the hash comes from the same Google server as the file, so it protects against corruption and truncation, not against Google's index or storage being compromised (there is no published signature for Chrome for Testing to pin). `--no-browser-download` turns the download off (the panel then offers a 「下載瀏覽器」 button instead); tests never download.

**Network-layer gate.** The action layer (button labels, form fields, checkout pages) can be dodged by a page whose harmless-looking button runs `fetch('/api/checkout', {method:'POST'})`. So every Space tab — and its out-of-process iframes and workers, which start paused until interception is on — runs with the CDP `Fetch` domain at the request stage (Document, XHR, Fetch, Ping, EventSource, Other). GET / HEAD / OPTIONS pass. A POST / PUT / PATCH / DELETE is classified (`classifyRequest`): `DELETE`; paths like `/checkout`, `/pay`, `/orders/place`, `/delete`, `/messages/send`, `/comments`, `/posts`, `/publish`; `?action=delete`-style queries; card fields (`cc-number`, `cvc`, …) or password fields in urlencoded / multipart / JSON bodies; GraphQL mutation names (`DeleteRepository`, `createTweet`, …); and the payment-domain rules. Payment / send / delete / publish then continue only if the agent step that caused them was authorized for exactly that class (for the step and 3 s after it, so a click's late request still counts), or a person approves a new card: the request stays paused while an ordinary approval card goes through the core's `ActionGateway` (audit row first, shown in the run that owns the Space, answered on the desktop or a phone). One card per class per step; a yes covers the rest of that step's requests of the class. No run to show the card in, a deny rule, the turn being stopped, the Space closing, or 10 minutes without an answer all **block** the request (`BlockedByClient`, the page sees a network error) and the card expires. A person driving the Space (接手) is never gated; the person's own tabs are never intercepted. The model is told in the step result what was blocked or let through.

**What the network gate does not catch.** Only known shapes: a payment API under an innocuous path with no card field (`POST /api/v2/x`) passes as a plain write. A popup's very first request can race the gate attaching to it. A sign-in POST with a password counts as `send` (one card per sign-in under 自主; approve it, or sign in yourself with 接手). It is a second layer beside the action layer and the person's card, not a guarantee. WebSocket, WebRTC and service workers: next paragraph.

**WebSocket, WebRTC, service workers (next round R3).** The same gate, the same classes, the same cards; nothing here can be switched off, and none of it applies to a person driving (接手) or to the person's own tabs.

- **Service workers: held.** Every Space tab and out-of-process frame runs with `Network.setBypassServiceWorker`, so the page's own requests never go through a worker (they reach the tab's `Fetch` gate instead; a site that relies on its worker's cache or offline page loads from the network in a Space). A worker's own requests (background sync, a message handler, `importScripts`) are gated too: the host auto-attaches service and shared workers at the browser level, paused; a worker in a Space's isolated context, in a Space's own (persistent) browser, or — in the shared profile — on the origin of a Space tab gets the same `Fetch` gate before it runs, and a worker the gate cannot attach to is closed. A worker of the person's own browsing runs untouched. In the shared profile a worker the person opened on the same origin as a Space tab is gated as well (only ever more cards, never fewer).
- **WebRTC: refused in agent tabs.** A script injected into every Space tab and frame before any page script replaces `RTCPeerConnection` / `webkitRTCPeerConnection` / `RTCDataChannel` with constructors that throw `NotAllowedError` (CI Chromium: refused in the tab and in a new same-origin `about:blank` frame). Defence in depth, not a guarantee: a context the script does not reach (a worker, a frame Chromium does not report) may still have the real constructor. Chromium is also started with `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`; in CI Chromium that switch did **not** stop two peers in one non-Space tab from opening a loopback data channel, so it is not a lock — the script is. The refusal is reported back through a CDP binding (`__alcaRtc`), which Chromium delivers only to a client with the `Runtime` domain on; Alca leaves `Runtime` off (it is a known automation signal), so in practice the refusal is not noted in the step or audited.
- **WebSocket: watched, then stopped after the fact.** CDP cannot hold a WebSocket (CI Chromium refuses a `Fetch.enable` filter for the `WebSocket` resource type outright, and no `Fetch.requestPaused` arrives for one). A Space tab's sockets are watched (`Network.webSocketCreated` / `webSocketFrameSent`) and classified with the request gate's own rules (`classifyChannel`: GraphQL mutation names, password / card fields in a JSON text frame, the sensitive-site domain rules on the socket's or the page's host; binary frames are not read). While the agent drives and a frame classifies as payment / send / delete / publish that the step was not granted, the tab is sent to `about:blank` (every socket on the page closes), the step result says the action **may already have happened**, the run gets a notice (not an approval card — there is nothing left to approve) and the audit log a `browser.channel.stopped` row. **The frame that triggered it has already left**: this cannot stop the first one. After two stops on one host a Space stops that host's sockets as soon as they open. Marking a site as `send` in the sensitive-site rules makes its sockets stop at their first frame. Holding sockets before they connect needs a local proxy; not built.

**Chrome cookie import (macOS, opt-in).** Never automatic and never into the shared profile. In a Space that is 「隔離並保留登入」 (its own Chromium and profile dir), 從 Chrome 匯入登入… lists the sites in a chosen Chrome profile — reading only host names from a private temp copy of `Cookies`, with no Keychain prompt. 匯入 then reads the "Chrome Safe Storage" password from the login Keychain (macOS asks the person; denying stops the import), derives the AES-128 key (PBKDF2-SHA1, `saltysalt`, 1003 rounds), decrypts only the picked sites' cookies in memory (`v10`, AES-128-CBC; Chrome 130+'s SHA-256(host) prefix dropped), drops expired ones, and sets them in that Space's browser with `Storage.setCookies`. The temp copy is deleted at once; cookie values are never written to Alca's database or logs; an audit row records the profile, the sites and the counts. Closing and deleting the Space removes them. The target Space is checked **before** the Keychain prompt, so a password is never asked for an import that would be refused. **Risks to weigh:** the imported sessions are live logins — the bot that owns the Space can act as you on those sites (always-confirm actions still ask); pick only the sites the task needs. Windows (Chrome 127+ App-Bound Encryption) and Linux are not supported and will not be worked around. The phone cannot start an import.

## WebRTC direct path (P13)

- **Off by default.** Nothing is built in: the core offers WebRTC only when settings `engineering.rtc.iceServers` lists STUN servers (≤ 4, `stun:` / `stuns:`, no credentials; TURN is refused). Empty = relay only, and devices never try.
- **Trust model.** WebRTC is a transport, never a security layer we rely on. Signaling (`rtc.offer` → answer) rides the existing sealed, signed Link session, so the relay never sees SDP, ICE candidates or DTLS fingerprints and cannot splice itself in. On the DataChannel the full signed session handshake runs again against the pinned core and device keys, and every frame is sealed again (AES-256-GCM, strict counters); DTLS is an extra outer layer. The core binds the channel's session to the device whose session asked; a channel that authenticates as another device is closed. Limits: one setup per device at a time, 8 pending in all, SDP ≤ 16 KiB, a 4 MiB message cap, 20 s to set up.
- **IP address exposure.** ICE shares addresses between the two ends — each learns the other's local and public (server-reflexive) addresses — and the STUN servers named in settings learn both ends' public addresses and that they use them. Only a paired, authenticated device ever receives the core's candidates (the offer is answered inside its session), but a phone you pair learns where the computer is reachable, and a STUN operator learns when you use Alca. Browsers hide local addresses behind mDNS names unless the page has camera / microphone permission; the core's side (werift) does not. Leave the list empty when that matters; the relay path reveals neither end's address to the other.
- **Failure is harmless.** Any error, a timeout or a drop sends the device straight back to the relay session it still has; the core binds ephemeral UDP ports only while a channel is being set up or is open, and on them answers only ICE checks with the credentials from that offer, then DTLS and the signed Link handshake — no service of the computer is reachable through them.

## Offline cache and outbox on the phone (P13)

- **What is kept.** For the newest 30 conversations, their last 200 messages (tool rows dropped), the conversation list and the team view; and the outbox of messages typed while offline. All in IndexedDB, every record sealed with AES-256-GCM under a data key wrapped by a non-extractable WebCrypto key (`apps/phone-pwa/app/cache-crypto.ts`). The AAD binds each record to its name and to this pairing's device id, so records cannot be swapped or moved to another pairing. Revoking the phone or forgetting the computer destroys the keys first (crypto-shredding), then the records.
- **Limits of that encryption.** The wrapping key (KEK) and the ciphertext sit side by side in the same IndexedDB database (`k:kek` next to the records). "Non-extractable" only stops _script_ from exporting the key bytes; the browser itself still persists them in its profile, next to the data. So the encryption guards against reading individual records out of context (another origin's bug that leaks bytes, a tool that dumps one store, a record moved to another name or pairing) and makes revoking crypto-shredding; it does **not** protect against anyone who can read the browser profile as a whole (a full unencrypted device or desktop-browser backup, a forensic copy, malware running as the user, the profile copied into another browser) — that reader gets the KEK and the data together. Against those, the phone's own device encryption and passcode are what protect the cache. It also does not protect against code running in the app's own origin (an XSS or a malicious service-worker update could ask WebCrypto to decrypt, since the non-extractable key is usable by script), nor against an unlocked phone in someone else's hands — the app opens and shows the saved copy, as it would show the live one. The key lives in the same browser storage as the data: clearing site data, Safari's storage eviction or a new pairing loses the cache (it is a cache, never the only copy; the computer has everything). There is no user passphrase.
- **Exactly once.** Each queued message carries a random client key; the core reserves the key before sending and finishes it after, so a retried flush — after a lost answer, a dropped connection or a core restart — never sends the same message twice (PROTOCOL.md § P13). A crash between the send and storing its result is resolved by finding the message itself; the narrow false match is the same text sent by the same device on the same thread within that minute under a key that has no stored result.
- **Read-only offline.** While the computer is unreachable the phone shows the saved copy, marked as saved and how old it is; approvals, questions, stopping a run and anything else that needs the computer are not offered, and nothing typed is sent until the session is back.

It then gets the approve key for this run of the core — and the person's own window fails its exchange and says loudly that the link was already used (`failedExchanges` is counted). The shell's codes go over a pipe and do not have this exposure; the browser itself also keeps the URL (with fragment) in its history.
- **A process that can drive the person's browser or the shell's window** (accessibility automation, a malicious browser extension on `127.0.0.1`) can press 允許 like the person. The approve key raises the bar from "read a file" to "control a window".
- **Real CLIs not run.** S1 and the stdin launch codes were tested with fake CLIs and on Linux; whether a real Claude Code login survives `--setting-sources ""`, whether Codex finds a keyring login from the isolated `CODEX_HOME`, and approving from the Tauri window on a Mac are on [DEVICE-TEST.md](DEVICE-TEST.md) § L.

## Mac test 2026-11-04b: background tools, outside writes, the bridge token, the keychain

- **Engine background tools (A8, `1fd9d88`).** Claude Code 2.1's `CronCreate`, `CronDelete`, `CronList`, `ScheduleWakeup`, `RemoteTrigger`, `PushNotification`, `Agent` / `Task`, `Skill`, `EnterWorktree` / `ExitWorktree` never call the permission tool, so a router could schedule a prompt into its own long-lived process. They are in `--disallowedTools` on every launch; the router runs on an allowlist (`--tools AskUserQuestion,ToolSearch`), so a built-in a newer CLI adds is absent too. If a CLI runs one anyway, the core refuses it in every role and at every level, stops the run and ends that engine process so a session-only job cannot survive. Scheduling belongs to 例行工作, which asks and is visible.
- **Writes outside the work folder from a shell command (A9, `c97a69c`).** The guard reads a command line's write targets (redirections, `tee`, `cp` / `mv` / `install` / `ln` / `rsync` / `scp` destinations, `touch`, `mkdir`, `rm`, `chmod`, `sed -i`, `dd of=`, `curl -o`, `wget -O`; `cd` earlier in the line moves relative paths; `~` and `$HOME` expanded). A target outside the work folder asks at every level, including 自主; a target from another variable, a substitution or a glob counts as outside. Alca's file tools expand `~/…` to the home folder (outside, so they ask) instead of writing `<work>/~/…`. Limit: a script file the bot wrote and runs is still not read (see Still open above).
- **Read-only lines with `$?` (A4).** A line of read-only commands joined by `;`, `&&`, `||` or a pipe is read part by part, and plain `$X` / `${X}` and special parameters (`$?`, `$#`, `$$`, `$!`, `$0`…`$9`, `$@`, `$*`) in arguments are only text, so `ls; echo "exit: $?"` needs no card. Arithmetic on digits and special parameters (`$(( $? + 1 ))`) is not read as a command. These still ask at every level: a command substitution or backticks Alca cannot read, `eval`, a variable or substitution as the program, `${!X}` / `${X@P}` (the value is expanded again), `$'\x…'` escapes, and arithmetic on a named variable (`$((X))`, `let`, `[[ $N -gt 3 ]]` — bash evaluates `a[$(cmd)]` inside the value). Writes are never "read-only" (the A9 check reads their targets).
- **The bridge token is not on a command line (E1, `8d668ed`).** It used to ride in `--mcp-config`'s JSON, visible to every local user through `ps`. Claude Code's MCP servers now get `ALCA_BRIDGE_FILE`, a 0600 file in the engine's 0700 temp folder.
- **The keychain is touched only when a secret is kept (E7, `1e673b0`).** No read or probe write at start; the first saved secret creates one item (account `vault-key` for `~/.alca`, `vault-key-<hash of the folder>` for any other data folder), else a 0600 `vault.key`. `ALCA_VAULT_BACKEND=file` keeps the keychain out entirely.
- Regression tests for the earlier fixes as the Mac saw them (`08e8a94`): the data folder's `config.json` / `secrets.json` refused to Claude Code's Read under 每步確認 with no card (E2); `core.log` written through a launchd-style fd has no token and ends 0600 (E3); the literal `~/.ssh` refused as a work folder through the API (E4).
- Untested on a real Mac: all of the above with the real `claude` CLI and the real login keychain (DEVICE-TEST § F, § P).

## Add-ons, 主動留意, reply check (P14)

**No outside code.** The add-on registry is a static list compiled into the program. No add-on is downloaded, installed or loaded from a path, there are no third-party add-ons, and an add-on's settings are data checked by its own schema (unknown or out-of-range values are refused) — never code or a prompt the add-on runs.

**Off by default, per bot, capped.** Every add-on starts off for every bot. One that spends model usage has a daily token and run cap per bot, counted per local day; at the cap it stops until the next day and the surfaces say so. Turning one on or changing it from the phone needs the `approve` scope; reading the list needs `chat`.

**主動留意 only reads.** Its scan reads with no model. Calendar and mail reach it only through the bot's connected-app grants, and only the subject, sender, date and a preview — never full bodies or attachments. The candidate call is one tool-less completion (every permission denied); its output must match a schema and may only cite evidence the scan produced, else it is dropped. The homework worker is read-only: anything other than reading and search is refused before the action gateway, so it cannot even raise a card. The add-on itself never sends, posts, pays or deletes; 好 starts an ordinary worker at the bot's level, where always-confirm classes still ask. Evidence and the offer text are fenced with `defuseAlcaTags` before reaching a model. The person's 「別再提這類」 is a suppress preference only the person can remove. The Web Push for a card carries only its kind and id.

**Reply check cannot add capability.** The check and the rewrite are tool-less completions with every permission denied; the reply, memories and must-follow lines are fenced as data. A rewrite can only replace the text of a reply that was already sent; it cannot call tools, answer cards or start work, and a rewrite that still breaks a plain rule is not used. The model it runs on is the bot's router model or one of the bot's own configured model services — the server refuses anything else — so picking a model never sends the conversation to a service the person did not set up.

**Must-follow and offers stay local.** `applies_to`, `due_at`, suppress preferences and the offer ledger live in the local SQLite file under the same rules as memory (append-only content, a decided offer is final).

## General harness: web_fetch, browser_script, vault passwords (worker harness Phase 4)

**`web_fetch` cannot reach inside.** Only `http`/`https` URLs without credentials. The host is resolved first and every address it resolves to must be public — loopback, private, link-local (including the cloud metadata address), CGNAT, multicast, reserved and documentation ranges are refused, in every spelling (decimal / hex IPv4, IPv4-mapped and NAT64 IPv6). The connection goes to the address that was checked (pinned in the socket's lookup), so a second DNS answer cannot swap it, and every redirect hop (at most 5) is checked again. At most 2 MB is read; only text is accepted; the text reaches the model fenced as untrusted external content (`<alca:external trust="untrusted">`, tag look-alikes defused). It is a read-class tool. `web_search` exists only while the person has picked a search provider (see “Web search and MCP servers”); without one, searching goes through Alca Browser.

**`browser_script` runs no page JavaScript.** The script runs in a QuickJS (WASM) interpreter inside the host with no network, files, modules, process or timers, and hard limits on steps (200), memory (64 MB), stack, wall time (≤ 120 s), returned value and log. Each helper is one ordinary browser step through the Space's ownership, takeover and sensitive-action gate; a send / pay / submit step stops the script and must be called on its own so the host shows the card. `css(…)` targets are matched with the DevTools DOM query (no page script) and only elements already in the snapshot can be acted on, so every step still has a role and a name for the gate. `hover` is not a mutating step; `setChecked` is gated like a click.

**Vault passwords go host → page only.** `browser_fill_secret` takes a vault item id, never a value. The value is filled only into a password field, only on an `https` page whose origin is exactly the item's origin (no subdomains, no `http`, no other port), only for a bot the item allows, and never on a site a script touched in the same task. The value is not recorded in the Space's replayable recording, the step's event label is generic, and every later output of that Space (snapshots, reads, errors) is redacted with the filled values, so it appears in no tool result, event, ledger row, message or log (asserted by a test that scans every store table and event stream). Site passwords are kept as `site-login:<id>` entries in the connectors' sealed vault.

**Background general workers cannot ask.** 提前做 runs on the general harness with the gateway's `noAsk`; 主動留意's homework runs on it with the read-only `restrict` (checked after the tool's inspection, so a `tool_call` to a write tool is refused too); a takeover is refused for work nobody is watching. `await_event` cannot end another task's wait (there is no `close_wait`); at most 20 event waits are open per bot.

## Worker harness: 完全授權, snapshots, coding tools, shell classification

**完全授權 (`full_access`) lets less ask, never everything** (`packages/policy/src/full-access.ts`). Without a card: changing files, running commands and network calls (write / execute / network); a plain `git push` (optionally `git -C <dir> push`, never with a `-c` that could alias it — every part of the line the classifier calls a publish must be one); deleting files inside or outside the work folder (shell `rm`, `rmdir`, `unlink`, `find -delete`, `git clean`, an ACP agent's native delete). Still asking: payments and outward sends (mail, messages, POSTs) — one such part anywhere in a command line keeps the whole call asking; `npm publish` and every other publish that is not a plain push; database deletes (`DROP`, `TRUNCATE`, `DELETE FROM`); a connected app's delete tool; writes outside the work folder still raise a card. Every call that ran only because of the level is written to the hash-chained audit log and to the dispatch ledger as `auto_allowed` (`放行原因：完全授權`) and shown in the worker panel. ACP agents never go past their autonomous native mode.

**Only the person on the computer can turn it on.** It is a separate column (`bots.full_access`, migration 19), off by default. The desktop bot editor shows a warning and a second confirmation (「我了解，開啟完全授權」) before it is on (`apps/desktop/ui/bot-advanced.ts`). On the server, `POST /api/bots` / `PATCH /api/bots/:id` turning it on need the approve key (`carriedApproveKey` in `apps/desktop/src/ui-session.ts`, checked in `team-api.ts`); a bare local token gets `403`, and `TeamApi` assumes no key for every other caller. The phone cannot turn it on (`link-team-ops.ts` refuses it) and can only turn it off; turning it off never needs a key.

**Snapshots keep a way back** (`packages/core/src/harness/git-snapshots.ts`). Before every coding turn at 完全授權 the host keeps a hidden ref `refs/alca/snapshots/<dispatch>/<n>`; when it cannot (no work folder, not a git repository, git fails) the turn does not start. At most 20 per repository (oldest removed first), kept seven days after the dispatch settled, swept at most hourly, `git gc` at most once a day per repository. A restore only takes a ref the ledger knows (`git_snapshots`) and keeps the current files as one more snapshot first; branches and commits are not moved. Restore and purge ask once more in the UI.

**`web_fetch` and vault passwords**: see the General harness section above — public addresses only, checked after DNS and pinned, every redirect re-checked; passwords only, `https` and exact origin only, the value in no event, table or log.

**Coding tools** (`packages/core/src/harness/coding/*`, Alca's own loop only):

- `bash` passes a filtered environment (`cleanEnv` in `bash.ts`): only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR` / `TEMP` / `TMP`, `LANG` and `LC_*` survive, and any name containing KEY, SECRET, TOKEN, PASSWORD or CREDENTIAL is dropped. When bash is on the machine, commands and host checks run with `bash -o pipefail -c` (`shell.ts`), so `false | true` is a failure; under plain `sh` a piped command is annotated that its exit code may be lost. A session's whole process group is killed on stop, on release and when its shell exits.
- **OS sandbox.** At 自主 and 完全授權 (or always, per bot) a command runs inside the OS sandbox: see § OS sandbox below. Without one it runs with the core user's rights, and the gate's classification, `ownsPaths`, approval cards and (at 完全授權) snapshots are the protection.
- edit / write / apply_patch refuse to rewrite a file that is not valid UTF-8 (`text.ts`), so a Big5 or binary file is never re-encoded silently; read marks it. Writes are read back and hash-checked; apply_patch checks for a stale read and runs under `withFileLock`.
- Writes outside a worker's `ownsPaths` raise a card at every level.

**Shell-running tools are classified by their command** (`packages/policy/src/shell-tools.ts`). One list names every tool that runs a shell command: `Bash`, `bash`, `hands_run`, `shell`, `exec_command`, `local_shell` (`bash_input` reads its `input`; ACP tools by `kind: "execute"`). `classifyToolCall`, `shellCommandOf`, the shell review, the actions record and the workspace guards all use it, so `git push` through `shell` or `hands_run` asks as a publish exactly like `Bash`. The command can only raise the declared class to an always-confirm class (publish, send, payment, delete), never lower it. Recognised build / test / format commands inside the work folder count as writes (`dev-commands.ts`); a bare `npx` does not (it may download first).

## OS sandbox (next round Phase C)

What the model's own commands can touch, enforced by the operating system rather than by reading the command line. One entry point (`@alca/os` `confine`), one policy source (the work-folder guards), and it never loosens a card: the gate classifies and asks exactly as before.

- **Which commands.** Alca's own loop: `bash` / `bash_input`, the host's check commands after a coding turn, the reviewer's commands. Claude Code: its Bash (and its child processes) through Claude Code's own sandbox, switched on in the `--settings` Alca passes (`failIfUnavailable`, no unsandboxed retry, Bash still goes through Alca's permission tool). Codex: its own sandbox, with `writableRoots` set to the work folder and `networkAccess` from the bot's setting. An ACP agent: the whole agent process inside the sandbox, writable work folder plus the state folders its engine setting declares; one that declares none does not run while the sandbox is on (the turn says why). ripgrep, Alca's own git and the browser are not wrapped (they run no model-chosen program).
- **What it enforces.** Writes only inside the work folder, the session's own temp folder (`TMPDIR`) and the package caches (npm, pnpm, Yarn, pip, Cargo, Go modules) or folders the bot was given. Not writable even inside the work folder: `.git/config`, `.git/hooks` and the engine / tool configuration the guards protect (`.claude`, `.codex`, `.mcp.json`, `.envrc`, …). Not readable: Alca's data folder (vault, database, logs, other bots' folders) and the home folder's secrets (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.netrc`, git and Docker credentials, `~/.kube`, the Claude / Codex login files, `~/Library/Keychains`). macOS: Seatbelt (`sandbox-exec`) with an `(allow default)` base and explicit denies (a deny-default profile stops zsh on macOS 26), the keychain services refused, connections back to Alca's own port refused. Linux: bubblewrap (`--ro-bind / /`, the writable folders bound back, a tmpfs or `/dev/null` over each unreadable path, `--die-with-parent`). Windows: none.
- **When.** Per bot (`bots.sandbox`, migration 24): 自動 (default: on at 自主 and 完全授權), 一律開, 關; network 可連網 (default) or 不連網. Loosening (關, 可連網, an extra writable folder) needs the approve key; the phone can only tighten. The worker panel (desktop and phone) labels each worker's state.
- **No sandbox here.** When the setting wants one and this computer has none (no `sandbox-exec`, no bubblewrap or user namespaces blocked by AppArmor, Windows), the work **still runs** — 完全授權 included, the person's decision of 2026-11-05 — with a warning on the worker panel and one `sandbox.unavailable` audit row per bot per start. Only 一律開 fails closed: the turn is refused (Claude Code: `failIfUnavailable`).
- **The one way out.** A command the sandbox stopped can be re-run with `unsandboxed: true`, which asks at every level, 完全授權 included; the card says the command runs outside the sandbox with your rights.
- **Alca's own git is hardened** (snapshots and the reviewer): `core.fsmonitor=false`, `core.hooksPath=/dev/null`, no `sshCommand`, no external diff or textconv, no pager, `GIT_CONFIG_NOSYSTEM=1`, so a work folder's `.git/config` runs nothing of Alca's.

**What it does not do (honest limits):**

- **bubblewrap can only cover paths that exist.** A denied file or folder that does not exist when the command starts is not masked; if something creates it during the session (another process, Alca itself creating the vault on first use), the sandboxed command can read it. The gate's string checks on paths still apply. Seatbelt rules are by path and do not have this gap.
- **Network is all or nothing**, and open by default. On Linux an open network includes loopback, so Alca's local API is reachable (its token is in the unreadable data folder and approving needs the approve key). No per-domain allowlist.
- **Claude Code's file tools are not in the sandbox.** Its sandbox covers Bash and what Bash starts; Read / Edit / Write / WebFetch, its MCP servers and hooks run outside it. Those stay behind Alca's gate (writes outside the folder ask at every level, protected configuration asks), Claude Code's own deny rules and the permission tool, not the OS. Whether `allowedDomains: ["*"]` means "every domain" for 可連網 is not verified on a real CLI (DEVICE-TEST § R).
- **Codex can read the whole machine.** Its sandbox limits writes and network; reads are not limited, so Alca's data folder and `~/.ssh` are readable to a command Codex runs. A read of the data folder is detected only afterwards in Codex's event stream (see § Review 2026-11-04b). Codex's protocol fields were not checked against a real Codex.
- **WebSocket's first message cannot be stopped** (see the browser section above); the browser is not inside this sandbox — the sandbox's network setting does not apply to it. A bot that should not go online at all should not have the browser tools.
- A program inside can still read most files outside the denied lists and use up CPU, memory and disk. `sandbox-exec` is deprecated by Apple though still working on macOS 26; the profile lives in one function.

## Data retention and the audit check (next round §3 / §4)

**What is kept how long** (user decision, 2026-11-05): the audit log forever (no setting); messages until the person deletes the conversation; `run_events` of finished runs and `job_events` of finished jobs 90 days; outside content and side logs (`trigger_events`, `spills`, `watchdog_events`, `peer_events`, `routine_runs` — each routine keeps its newest 20) 90 days; daily backups 7. Settings `engineering.retention` (7–3650 days; `dailyBackups` 0–60). Dispatches stay at 30 days as before.

**Controlled append-only.** Those tables stay append-only for everything except two paths, enforced by their delete triggers (migration 21), not by the code: the retention sweep — only while its table's row in `retention_gate` is open (it opens and closes inside one transaction), only rows older than the gate, only when the gate itself is at least seven days in the past, and only rows whose owner is finished — and deleting a conversation, once `threads.deleted_at` is set (it can never be cleared). A bug that selects the wrong rows aborts the whole statement. `audit_log` has no gate and its triggers still refuse every UPDATE and DELETE. Someone who can write the database file outside Alca can still drop triggers; that is what the audit check is for.

**The audit check.** One verifier (`verifyAudit`, streaming) serves `alca db verify`, 設定 → 資料 → 驗證稽核紀錄 and the hourly sweep (only the rows added since the last check). It recomputes the hash chain and compares the end of the log with an anchor kept outside the database (`<data>/audit.anchor`, 0600, rewritten after each passing check), so it also catches the newest rows cut off or an older backup put back; restoring with `alca db restore` moves the anchor back with the backup. A failure leaves the anchor where it was, is logged, and raises one `system.alert` (the desktop shows a notice; phones are not pushed yet). **Limit:** an account that can rewrite both the database and the anchor file (the same user) is not stopped by it; the check guards against accidental rollbacks, wrong copies, disk damage and edits to the database alone.

## Deleting a conversation, export and import (next round R5, Phase F1)

**Content is really deleted.** Deleting a conversation (desktop, phone with `approve`, `DELETE /api/threads/:id`) sets `threads.deleted_at` (final) and, in one short transaction, deletes or blanks every row and column that carries its words: messages, drafts, engine sessions, approval and question cards (migration 22 lets them go only for a marked thread; without the mark the triggers still refuse), worker titles / goals / results, job titles / inputs / results, the dispatch ledger with its events and waits, early work, router and worker inbox rows, and the contents of undo snapshots. The event trail (`run_events`, `job_events`, spills) follows on the database worker in batches; a crash in between is finished by the next hourly prune. `secure_delete` zeroes the pages. One audit row `data.erased` records the scope and the options (never the content). Two choices on the dialog: 「連同從這段對話學到的記憶」 (off by default: memories are often preferences across conversations) and 「也從備份裡清除」 (on by default, `engineering.retention.scrubBackupsOnDelete` for callers that do not say): each backup file is rewritten through a temporary `VACUUM INTO` and renamed into place; a backup that could not be rewritten is logged and left as it was, never deleted.

**What stays, by design.** The `threads` row as an empty shell (id and times; runs, jobs and the audit log point at it) and the runs' ids and times; `audit_log`, permanent and hash-chained, whose `target` can name a recipient address or a URL (never the conversation's text); copies outside Alca (file-system snapshots, Time Machine, other copies of the data folder); and **the CLI engines' own session logs**: Claude Code keeps its transcript in its own folder, and Alca does not run it with a separate configuration folder (user decision 2026-11-05), so those logs are outside what a delete reaches — clear them in Claude Code if needed. The dialogs say so. Memories removed with 「連同記憶」 are deleted with all their versions but get no tombstone (they can be learned again); 忘記 on the memory page still writes one.

**Export.** One conversation goes to a `.alca-export` file (gzip JSON Lines; `POST /api/export` with the local token, the conversation row's 匯出, 設定 → 資料, `alca export thread <id>`). It holds the conversation's full text: without a passphrase the file is plaintext (0600 when the CLI writes it; a browser download takes the browser's mode); with one it is sealed with AES-256-GCM under a scrypt key, the manifest authenticated as associated data. Engine sessions, the audit log, connected-app grants and every secret are never in it. The core writes the file to `<data>/exports` (0700) only for the time the download takes and removes it.

**Import widens, so it needs the approve key.** `POST /api/import` adds a conversation, so like approving and pairing it needs the in-memory approve key of a window Alca opened (`ui-session.ts` NEEDS_KEY, mirrored in the window's list; a test keeps the two equal). It only adds — every row gets a new id, a deleted conversation comes back as a new one — in one transaction on the database worker, at most 2 million rows, and a file from a newer schema is refused. One audit row `data.restored`. `alca import` therefore runs only with the core stopped (it opens the store itself, migrations first); beside a running core it points to 設定 → 資料 → 匯入.

## The core's keys in the vault (next round §6, Phase D1)

**Where each secret is.** The Link identity (`core.linkIdentity`, the ECDSA P-256 key every paired phone pins) and the VAPID key (`core.vapidKey`) are entries in the same sealed `vault.json` as the API keys; the vault's file key is in the macOS Keychain (`security`, written over stdin) or the freedesktop Secret Service (`secret-tool`, value on stdin, read back after storing). `secrets.json` keeps only the loopback token `core.localToken` and the marker `core.secretsIn: "vault"`: `alca open`, `desktop:pair` and the desktop shell read the token there, and approving needs the in-memory approve key anyway. The keys are not written back to `secrets.json` (no plaintext double-write, user decision 2026-11-05). The data folder opens one `Vault` instance (`openDataDir`); connectors, providers, Telegram, site logins and the core keys all use it. Phase F2's data key is the entry `core.dbKey` (`@alca/os` `ensureDataKey` / `getDataKey`, see ARCHITECTURE and the next section).

**What this protects against.** Someone who gets the data folder's files but not the keychain: a Time Machine or cloud copy of `~/.alca`, another account reading a folder whose modes were widened, a copied disk image. It does **not** protect against a program running as the same user, which can ask the keychain for the vault key (on macOS without a prompt for an item `security` created — to be confirmed on a real Mac, DEVICE-TEST § P); that is the OS sandbox's job (§5).

**Degraded, and said so.** With no keychain (Windows, Linux without a Secret Service or D-Bus session, `ALCA_VAULT_BACKEND=file`, a keychain that refuses) the vault key is a 0600 `vault.key` next to the vault: about the same protection as the old plaintext 0600 file. This is no longer silent: the core logs where the key is and why at every start (a warning when it fell back, information when the file was asked for), and `alca secrets status` prints the same line. A keychain that does not answer (locked, refused, no D-Bus) is never read as "no key": a vault that exists and cannot get its key does not open, and no new key or identity is made.

**The move and its failures.** On the first start of this version an older folder's keys are written into the vault in one write, read back from the file (not a cache), and only then removed from `secrets.json` — and from `secrets.json.bak`, which is rewritten with the same content so the old plaintext does not stay in the backup (a `.bak` that still holds keys the main file no longer has is rewritten on any later start). If the vault write or the read-back fails, `secrets.json` is not touched and the core runs on its values; the next start tries again. While `secrets.json` still has a key, that copy wins over a different one in the vault (it is the one paired phones pin). One audit row `secrets.migrated` records the move (names and backend only). Left-over `secrets.json.corrupt-*` / `*.reset-*` copies from older recoveries may still hold the keys in plaintext; `alca secrets status` lists them.

**Never a silent new identity.** A new identity is made only when the key is absent from both places and `secrets.json` does not say it was moved. A vault that does not open (its keychain item deleted, the folder copied to another computer or account), a marker without the entry, or a malformed entry stop the start with how to recover: `alca secrets export` on the old computer and `alca secrets import` here, or `alca secrets reset --confirm`.

**Export, import, downgrade.** `alca secrets export --to-file <path> --confirm` (core stopped, never overwrites, 0600) writes the token, the two keys under their pre-D1 names and every other `core.*` entry (later `core.dbKey`) as one plaintext file — the format an older version reads as `secrets.json`, which is the downgrade path (an older version would otherwise make a new identity). Anyone holding that file can impersonate this computer: delete it after use. `alca secrets import <path> --confirm` writes the keys into this folder's vault (read back) and the token into `secrets.json`, keeping the previous `secrets.json` as `.reset-<time>`. `alca secrets reset --confirm` removes only the identity and the push key from the vault (API keys and `core.dbKey` stay); when the vault does not open it sets `vault.json`, its `.bak` and `vault.key` aside as well. The daily database backups do not contain the vault.

## Column encryption at rest (next round R7, Phase F2)

**What is sealed.** The content columns of the database — `messages.content`, `run_events.payload`, `job_events.payload`, `jobs.title` / `input` / `result` (since migration 28; a turn job's title is the fixed word `turn` and a worker's job no longer copies its title or goal), `spills.body`, `trigger_events.payload`, `router_inbox.body`, `worker_inbox.body`, `workers.goal` / `result_summary`, `approvals.summary`, `dispatches.report`, `memories.body` / `quote`, `drafts.body`, `routine_items.payload`, `offers.text` / `action` (since migration 30: a 主動留意 offer is written from mail and calendar facts; its `topic`, category and evidence ids stay plain) — are written as `{"$enc":1,"k":<key id>,"d":"<base64 nonce‖ciphertext‖tag>"}`: AES-256-GCM (`node:crypto`) with the data key, a fresh 12-byte nonce each write, and `table|column|primary key` as associated data, so a value copied to another row or column does not open. One list (`SEALED`, `packages/store/src/seal.ts`) names them; a test fails when SQL outside the store's repos names one of them. `memories.search_terms` holds keyed tokens (HMAC-SHA256 with a sub-key `HKDF(key, "alca fts")`, 10 hex characters each), so the full-text index holds no readable word.

**The key.** One random 256-bit data key per data folder, the vault entry `core.dbKey` (D1's key ring: a rotation adds key 2 and old rows still open). Its protection is the vault key's — the OS keychain, or degraded the 0600 `vault.key`, in which case the data key is effectively next to the database; 設定 → 資料 → 加密 shows where the vault key is. Every start opens a check value (`meta.seal_check`); a database sealed with another key, or one whose key left the vault, stops the start before anything is written, and no new key is made over a sealed database (`DataKeyStartError`, `SealKeyMismatchError`).

**Older rows.** Rows written before the key existed are sealed by a background pass on the database worker (time-targeted batches, its place kept in `meta.seal_progress`, resumed after a restart; a minute after each start and then hourly). The append-only tables, resolved approvals, memories and offers (migration 30) are rewritten through a gate of the same kind as migration 21's: `seal_gate` is open only inside the pass's own transaction, and while open the trigger lets through only a content column going from plaintext to the sealed form with every other column unchanged. When the pass finishes the WAL is checkpointed and truncated; `secure_delete` already zeroed the old cells. A migration that adds a sealed column clears `done` in `meta.seal_progress`, so backups taken before the pass covers it count as plaintext again (migrations 28 and 30). The old backups still hold plaintext: 設定 → 資料 offers to delete them and take a new sealed backup, and (user decision 2026-11-05) refuses until no sealed column holds plaintext and the pass has finished; deleting them is behind the approve key and leaves one audit row `data.backups_dropped` (file names only). After that there is no downgrade path (an older Alca cannot read sealed columns; only a pre-migration backup is plaintext).

**What it stops.** Someone holding `state.sqlite`, its WAL, a backup, a Time Machine copy or a mis-shared data folder, without the keychain, reads no conversation, event or memory text. **What it does not:** a program running as the same user can ask the keychain for the vault key (§5's sandbox is that layer); and these stay plaintext by design — `audit_log` (hash-chained; its `target` / `detail` may name an address or URL), ids, times, statuses, conversation and worker titles, job titles / inputs / results, question cards, dispatch events, early-work goals, the memory `subject` key, connector and routine settings, and the JSON columns read with SQL (`workers.grants`, `routines.cursor`, `link_client_ops.result`, `harness_waits.questions`). Someone with the database but not the key can still see which memories share a keyed token and how often (as with tombstones). Losing `core.dbKey` loses the content: `alca secrets export` carries it.

**Backups, restore, export.** Backups (`VACUUM INTO`) copy the sealed values and open only with the same key ring. A restore refuses a backup sealed with another ring (checked with the key when the caller has it, otherwise by comparing the plain ring fingerprint `meta.seal_ring` with the database it replaces). A `.alca-export` file holds the conversation in plaintext (or under its own passphrase), so it does not depend on the key; an import seals the rows under their new ids.

## 續做, structured results, stream wakes and website logins (next round Phase D2)

**續做 never happens on its own.** A worker whose step budget runs out leaves its dispatch in `needs_review`; only the router (`worker_start { continueDispatch }`) or the person (`POST /api/workers/:id/continue` and the phone's `workers.continue`, both needing the approve key / `approve` scope, since each continuation spends another step budget) can continue it. The host refuses a seventh continuation and one after two continuations in a row that made no progress (no file changed, nothing outward, no check run); 72 hours without one settle it as `budget`. The resume is a compare-and-set inside the transaction that inserts the new worker, so two presses start one worker.

**Handoff file.** `<data>/handoffs/<dispatchId>-<n>.md` (folder 0700, file 0600, written atomically) holds the goal, the done-when, the files changed, the outward actions already done (not to be redone), the verification state, the last report and a todo snapshot, with every line passed through the memory secret redactor (`@alca/memory` `redact`: pattern-based, so a secret in an unusual shape can get through). It is removed by the hourly sweep once its dispatch row is gone (30-day prune, or deleting the conversation).

**What the continuation sees.** The continuation's task message is the **original goal text unchanged** — whatever the router or the person wrote, including anything secret they put in it; it is not redacted, as it was not for the first worker — followed by the handoff inside a fenced `<alca:handoff>` block (data, not instructions; Alca tags in it defused; at most 6000 chars). Only the handoff block is redacted. Do not put passwords in a task; use the vault.

**Structured results are checked locally.** `report_result.data` is checked against the dispatch's `resultSchema` with the same validator as tool arguments (only the supported subset, ≤ 8 KB); providers' strict-JSON modes are not relied on. A routine's result names only the item ids it was given (an enum), so a wrong id goes back to the model. The reviewer's `review_verdict` tool only hands the verdict to the host (`read`, no effect anywhere).

**Stream wakes.** An outside event wakes only waits of the same bot on that exact stream, after the trigger's rule filter, and reaches the continuation fenced as untrusted (`<alca:trigger … trust="untrusted">`, forged closing tags defused, long text spilled). A repeated event wakes a wait once. Woken workers keep their dispatch's grants and level; an event cannot widen them.

**The ledger on the wire.** `dispatch.event` carries only whitelisted short fields, never tool output, check output, a call's summary, a snapshot ref or a handoff path, and only rows whose transaction committed.

**Website logins.** Added on the desktop only (`POST /api/connectors/logins`, approve key); the phone lists and removes (`approve`) but cannot add, so a password never travels the relay. No response, log line or audit row carries the password (`site_login.saved` records origin, username and the number of bots); the list strips it in `SiteLogins.all`, and the phone keeps only the fields its row shows.

## Releases and updates (Phase E)

- **Release files**: every file is in `SHA256SUMS`; with the owner's release key (`ALCA_RELEASE_SIGNING_KEY`, Ed25519) `SHA256SUMS.sig` signs it. macOS builds are Developer ID signed and notarized only with the `APPLE_*` secrets (else ad-hoc), Windows builds Authenticode signed only with `WINDOWS_CERTIFICATE` (else unsigned); the release notes state which. `install.sh` / `install.ps1` refuse a tarball without a matching SHA-256.
- **`alca update`**: never installs on its own — the daily check (one anonymous GET to the GitHub release list; a private repo uses the user's own `gh` login; `engineering.updates.check: "off"` = no request) only notifies; installing is `alca update install` on the terminal after a yes. What it accepts is decided by the installed core: a core packed with `release-keys.json` installs only a release whose `SHA256SUMS` verifies against that key (missing or bad signature = refused); a core without one checks the checksum only and says so (that detects a damaged download, not a replaced release — anyone who can change the GitHub release can change its checksum too). The tarball's `ALCA_VERSION` must be the requested version (no replaying an older signed file as a newer one); downgrades need `--allow-downgrade`. Drafts are never offered.
- **Before replacing anything**: the new tree is unpacked beside the old one and run once; the background service is stopped; `state.sqlite` is backed up (the pre-migration backups' set); the old version stays as `app.prev`. A new version that does not answer `/api/health` within 30 s is rolled back automatically; a rollback after a migration restores the pre-update backup and moves the newer database aside (never deletes it).
- **Not covered**: the desktop App (Tauri) does not update itself yet; the core inside it only points to the new download. A compromised release key lets its holder ship updates to every core that trusts it: keep it offline, rotate as in RELEASE.md § 2.3.

## Web search and MCP servers (next round R1, R8)

**Web search sends the query out.** `web_search` is offered to general workers only after the person picks a provider in 設定 › 網路搜尋 (Brave Search or Tavily with the person's own API key, or a self-hosted SearXNG). Every search sends **the query text the model wrote** to that provider — and a query can carry details of the conversation (a name, an address, what the person is looking for). With Brave or Tavily the query reaches a third party under its own privacy terms, tied to the person's API key; with SearXNG it reaches the person's own instance, which in turn forwards it to the upstream engines it is configured for. Alca sends nothing else (no conversation, no memory, no cookies). The key is read from the vault per call, goes only into a request header and is scrubbed from errors. Requests go through `web_fetch`'s outbound path (resolved and pinned address, size cap, no redirects); the saved SearXNG origin is the one private address it may reach, origin for origin — `web_fetch` on a hit pointing there is still refused. Hits come back inside one untrusted `<alca:external source="web_search">` fence; a hit's URL is never fetched by the search.

**Two ways to connect an app, two levels of trust.** The model always sees the same three connector tools; the host decides the class of each call, asks for send / publish / delete / payment every time, counts one daily quota across all of them, and fences every result as untrusted app data. Gmail and Google Calendar come **only through Composio**: Google direct (Gmail / Calendar with the person's own OAuth client, refresh token in the vault) was removed on 2026-11-05 at the person's choice. Migration 27 disconnects any account it left (grants deleted, status removed, its triggers off) and the desktop deletes `integration.google.*` from the vault at start; the grant at Google itself is not revoked by Alca (the person removes it at myaccount.google.com/permissions). `engineering.google` remains only as 用 Google 帳號啟用遠端's client (an ID token for the relay, `openid email`; no Gmail or Calendar scope).

|                               | Composio                                                                      | The person's own MCP server                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Who holds the app tokens      | Composio (the person's Composio project)                                      | The server; any header / env secret the person gives is in the vault (`integration.mcp.<id>.<name>`), the table keeps names only                 |
| Where mail / data travels     | Through Composio                                                              | Wherever the server sends it (a stdio server runs on this computer; an HTTP server is whatever URL the person entered)                           |
| OAuth client                  | Composio's                                                                    | — (header tokens only; remote MCP OAuth is not supported)                                                                                        |
| How a call's class is decided | Slug verbs + Composio's tags (a `readOnlyHint` can make it a read, as before) | The same rule as Composio (slug verbs + the server's annotations); a tool the server cannot describe is a send unless its name is plainly a read |
| What its descriptions are     | Composio's text                                                               | Untrusted: tool descriptions are cut to 500 characters, fenced and defused before the model sees them                                            |
| Setting it up                 | Desktop or phone (approve scope)                                              | Desktop only; adding or changing a server needs the approve key (it adds a program that runs or an endpoint that is called)                      |

A stdio MCP server is a program the person chose, run with the core user's rights and an environment of the allow-listed variables plus its own secrets — the same trust as an ACP engine; a server that lies about its tools (a send tool annotated read-only and named like a read) is classed as a read, a risk the person accepted with policy decision 4. On the phone MCP accounts are visible and can be narrowed (lower a bot's access, disconnect) but never widened or set up.

## Known limits

- **Metadata at the relay.** It sees which device ids talk to which mailbox, when, from which addresses, and how much (video frames make activity visible). Self-hosting removes the third party; padding and cover traffic are not implemented.
- **Non-constant-time BigInt arithmetic in SPAKE2.** The blinding (`w·M`, `w·N`, unblinding) uses JavaScript BigInt point math, which is not constant time. It only ever touches public points and the password scalar `w`, which is derived from a single-use code that expires in minutes; the long-term keys and the ephemeral secret scalars stay inside WebCrypto. A timing attack would have to recover `w` within the code's lifetime from one run, and even then gets one pairing that the person sees in the device list.
- **A compromised phone** acts within its scopes until revoked (it can approve cards if it has `approve`). Grant `control_computer` only to phones you hold.
- **A compromised core** owns everything, including every paired hands machine's work directory. Hands commands run with the daemon user's rights inside that directory; the work directory is a boundary for paths, not a sandbox for processes (a command can still use the network or read world-readable files). Run hands as a dedicated user or in a container where that matters.
- **Denial of service** by the relay or the network is out of scope (the LAN path helps when available).
- Browser (P13): the network gate catches known request shapes only (see above); a WebSocket is stopped only after its first sensitive frame left, and WebRTC refusal rests on an injected script (R3); the Chrome for Testing hash is not a signature; the cookie import is macOS-only and was tested with a fixture database and a fake Keychain, not a real Chrome profile.
- P14: 主動留意 and 回覆檢查 were tested with fake engines only; a real model may propose weaker candidates or rewrites (the plain checks and caps still hold). The reply check runs after the reply was delivered, so a person may read the original before it is marked 已修改.
- General harness (Phase 4): `browser_script` has no `evaluate` — a script cannot run JavaScript in the page, so a value that only page script can compute must be read from a snapshot or not used. The vault fills **passwords only**: card numbers and one-time codes are not filled (the worker hands the Space to the person with `browser_request_takeover`). The origin check runs just before the fill; a page that navigates in the same instant is detected only after the fill (the step then reports an error). `web_fetch` checks the first resolved address it connects to and refuses a host when any of its addresses is non-public; it does not follow `<meta refresh>` or script redirects. Tested with a fake CDP and a fake resolver / connection only.
- Worker harness: the OS sandbox (above) covers model commands only where this computer has one, and not Claude Code's file tools or Codex's reads. `withFileLock` serialises writes inside one process only. At 完全授權, Codex coding runs with `on-request`, where commands inside its sandbox and patches inside the writable roots do not reach Alca's gate (no card, no per-file undo); the git snapshot before each turn is the way back. Card numbers and one-time codes are not filled. An event wait is woken by its clock or by an outside trigger on the stream it waits on (Phase D2; the event arrives fenced as untrusted data, after the trigger's rule filter). The environment filter hides secrets in environment variables only; without a sandbox, a command can still read files the core user can read.
- Not built yet: credentials injected into hands commands by the host, signed / notarized builds and a signed updater.
